# @contexera/dsh-agent-team/tools

[English](README.md) | 中文

面向 Agent Team Member 的模型工具。本包在调用方 Agent preset scope 内注册工具，不提供或替换 Host service。它不含 context 工具：Session 由引擎就地压缩，冷下来的一代由 Host 换代，两者都不是模型的决定。

## 工具

- `team_inbox` 列出调用方 Member 的有界未读 Thread 摘要，先按 direct work、再按最近活动排序；只有 Thread 存在真实 Task overlay 时才出现 Task standing。header 给出 unread/direct 总数与展示的 Threads 数（有界列表之外仍有未读时给出截断结论）；每个条目显示精确的 unread/direct 计数、Project ref 与 Task standing。页脚把阅读指向 `team_thread read`；渲染不携带 revision 与写令牌。
- `team_thread` 读取 Thread 或 Project 的 Main stream、分页历史，或按 ref 读回一条 Message。`threadRef` 是主身份；Thread 有 Task 时，`taskRef` 是 `read`/`history` 的别名；对 Thread 使用 `message` 时需要 `threadRef`（同时给出的 `taskRef` 必须指向同一个 Thread；Main stream 用 `projectRef`）。`beforeSequence`/`limit` 用于 history 分页，`read` 忽略它们，`message` 拒绝它们。三个 action 分开渲染：`read` 渲染结果、Thread 身份、导向（anchor 不是返回 fact 时给 bounded anchor subject）、Host 提供的背景（不是本次新确认的工作，当前上下文已完整可见时不重复）、只含 active Claims、已确认 Task reminders、带行内 unread/direct 标记的已确认 facts（正文已完整可见时渲染 `body already in current context; omitted`，仍计入确认；完整事件已在当前上下文中的 Activity 只渲染身份，标记 `complete event already in current context; omitted`）、当前 Task 卡（是状态，不是 Thread reading）、read-through/剩余未读页脚（只要这次 read 身后留有 Thread facts，页脚同时给出那些 facts 的数量）；`history` 渲染历史页（首页 full anchor、continuation 页 bounded subject，绝无当前 Claims 或上下文建议）；`message` 按 ref 逐字读回一条 Message。`read` 推进持久 watermark，是 next-write token 的读侧唯一来源——仅在未读清零时渲染；你自己的已提交 public mutation 也会回传一份新 token。没有 fact 或 reminder 可确认的 read 不推进状态，也不写 operation。只有 reminder 的 read 仍会确认提醒并报告提交。没有确认任何内容时，若无剩余则显示 `Read — no unread updates …`，否则显示 `Read — no facts acknowledged …`；画面来自当前 projection。Activity facts 只从事件本身渲染——activity ref、actor、Task 与 Thread refs，以及该事件记录的 Claim refs 或 transfer 两端，绝不用当前 Task/Claim 状态。确认仍为 done 状态 Task 的未读验收的那次 read，把这些事实写进 facts，且不对读取者的上下文给出任何建议：模型没有 context 工具，也没有代际选择。Agent 的 `read` 与 `message` 输出整体有界：工具少选几条 fact，超长 Message 正文按有序字符分段返回，read 遇到未完整 Message 就停下，不越过它确认。唯一续读方式是重复同一个请求，地址（以及 `messageRef`）不变；Host 从当前 Session surface 的第一个缺失段继续，没有 offset 参数。Activity 只有一行且不能分段：超出固定结果上限的 Activity 不确认任何内容，换更大的上下文模型也无法让它装入，结果会报告这个边界交由 Human 直接检查。Thread receipt 存储选中的界限，写入该字段之前的 receipt 仍按缺省 batch 解释。Main stream 的 read 补同样的近期 Message 背景，只确认被选中的前缀，并把 Thread 卡渲染在独立区，不因此把这些 Thread 标为已读。Human 的读取与 Remote 参数不变。
- `team_attention` 只回答你是否关注某个 Thread：`status` 只报告、不改变任何东西，`follow` 与 `unfollow` 改变 Attention。三者只接受一个地址——Thread（`threadRef`，或 Thread 有 Task 时的 `taskRef`）或 Project Main stream（`projectRef`），不可同时给两者——再加路由 Workspace，并渲染一行：Thread ref、可选 Task standing 与 following 状态。Attention 不是 reading：这里没有任何 action 渲染 Thread facts、确认未读或交写令牌，读一个 Thread 也从不改变你是否关注它。你自己在该 Thread 的 Task 上持有 active Claim 时，unfollow 会被拒绝，直到完成工作或 release 该 Claim。
- `team_message` 在 Project 的 Main stream 发言、创建顶层 Thread、回复既有 Thread。`start` 用 `kind: 'discussion'`（默认）或 `kind: 'task'` 原子创建 Task——已移除的 `asTask` 写法会被拒绝并指回 `kind`，绝不静默丢弃。Task start 另接受 `accountable`（Project owner 的 memberRef，或 `human`）与 `sourceThreadRefs`（派生自哪些讨论 Thread，卡片因此渲染在那里而非 Main stream）；两者在讨论 start 以及 `post`/`reply` 上都被拒绝而非丢弃，commit 的 start 回报实际记录的负责人。commit 的 start/reply 渲染一个 committed-verb 结果（Thread created / reply added），携带 Message、Thread 与可选 Task refs，以及恰好一个 next-write token hand-off。Reply 在检查令牌新鲜度前先拒绝未读工作。类型化拒绝以 `Not committed` 开头；完整且身份明确的 Message 与 Activity 事实可提供令牌供重新考虑，部分结果则指向 `read`。两者都不确认未读。模型可见结果不再暴露已退役的 v1 `undeliveredMentions` 字段；只有 Host replay 会读旧 receipt。
- `team_dm` 向同一 Workspace 内一个 enabled Agent Member 发送一条私有 direct message。它只接受 `memberRef` 与 `body`，别无其他——没有 Thread、没有 Task、没有写令牌、没有附件——多带的参数会被拒绝而不是被忽略。结果区分 `Delivered` 与 `Recorded, not delivered`（携带 delivery note 与禁止盲目重发的警告）；没有自动重投。Human 不能被 DM，DM 正文里的 mention 也不会通知任何人。
- `team_reminder` 为自己创建、列出或取消 reminder：一个绑定 Member 本身而非 Session 的时间承诺。`create` 取 `scheduleKind` 与该种类自己的字段（`once` + `at`、`every` + 至少 10 的 `minutes`、`cron` + 五个字段的 `expression`，按固定 UTC+8 读取），并且总要 `note`，最多 2000 字符。单个 Member 最多 50 个 active reminder；schedule 只报种类而不给该种类的字段会被拒绝，而不是被猜一个。`list` 报告你名下的全部 reminder 及其 state 与 occurrence 事实；`cancel` 按 `reminderRef` 撤回一个。到期的 occurrence 以私有通知进入你的 Team Inbox 并唤醒你，Host 在它真正进入某一轮次时记录 consumed，错过的恢复后补投一次。你 suspended 期间 reminder 继续计时；archived 或 removed 时全部取消。只有你能创建自己的；Human 从 Member 详情撤回。
- `team_subscription` 创建、列出、修改、测试、暂停、恢复、删除 Project 的脚本订阅，重设去重基线，或重放一次失败的投递。任何 Member 都能 `list` 与读 `logs`；写入只限 Project owner。create 与 update 会把脚本（最多 16 KiB）快照下来、跑一次试运行，试运行失败就拒绝写入；Host 对脚本逐行输出的 JSON 事件去重，每分钟最多发布 20 条。`logs` 渲染最近的运行及其 revision、触发方式、类别与事件数；owner 与 Human 还看得到失败原因和输出末尾。`deliveries` 列出自动重试用尽的 webhook 请求，`replay` 可以按当前定义或接收时的定义重跑一次。create、update 与 `reset_webhook` 可能武装一个 webhook 地址，由于 Host 只存它的哈希，完整地址只返回一次；同一 request id 的重试仍校验当前 Project 所有权，直接由账本答复，不再读脚本文件或检查凭据，并说明地址是否已不可取回。没有保存脚本路径的旧 create 或 update 拒绝该路径重试，并返回已提交的 subscription ref。
- `team_task` 通过 `board` 读取 Task board，通过 `list` 列出单个 Task 的 active Claims，通过 `claim`、`done`、`release` 修改调用方 Member 的 Direction Claim，通过 `accept`、`close`、`reopen`、`transfer` 了结或转交 Task，`promote` 则供 Project owner 把讨论 Thread 升格为 Task；它只适用于真实 Task。`board` 显示 open Task 与每个项目最近完成的 Task，每行给出 accountable owner，以及读者可验收时的待验收标记；`mine` 只留读者负责或正在执行的 Task。`list` 渲染 Task/Thread 身份与只有 active Claims 的 collision surface，且无写令牌。commit 的 mutation 点名动作（Claim created/completed/released、Thread promoted、Task accepted/closed/reopened/transferred），先渲染权威的受影响 Claim，再 hand-off 一个 next-write token。谁能 accept、close、reopen 或 transfer 由 Host 决定而非工具：工具只转发 action 与写令牌，`self_acceptance_forbidden` 或 `accountable_owner_required` 拒绝的出路来自 Host 的 recovery registry，并补上 Task 的当前状态与 accountable owner——那只有拒绝之后调用方自己才读得到。拒绝与 message 拒绝共享同一形式。Direction 互斥键执行 Unicode NFKC normalization、trim、空白压缩和确定性大小写折叠。
- `team_view` 是 address book：有界、按 membership 授权的 Project、顶层 Thread 与 Member 摘要——是当前的地址簿，不是工作队列。Threads 是唯一分页目录：newest-first 行携带 threadRef、Project ref、bounded anchor subject 与行内 Task standing（绝无第二个 Task 索引，也不渲染 revision 或消息数）。cursor 只延续 Thread 行；continuation 页只渲染 Threads，翻页可达全部获授权的顶层 Threads，包括 taskless 与不在首页的 taskful。
- `team_worker` 把一件自包含的工作交给本机 Worker 引擎（Codex 或 Claude Code），用它自己的工具、登录与设置执行；也能停止一次执行，给正在执行的 turn 补一句指令，或按编号只读查看一次执行的诊断。委派要给出 Thread、Task 或 Project，目标决定结果落在哪里：绑定执行把开始与结束发布到 Thread，答案进入发起成员的 Inbox；只绑定 Project 的执行不发布任何东西，答案回到调用方自己的 session。调用在执行被接受后立即返回，没有需要轮询的东西。`stop` 只接受本 session 发起过的一个 `worker:` 编号，并等待引擎确认清理，等待有界限：超过界限执行仍是 `running`、调用按 `worker_stop_pending` 拒绝；引擎报告清理失败时记为 `failed` 并附「清理未确认」说明，绝不会报成 `stopped`。`inspect` 接受同一个编号，回答 Thread 已经承载的摘要、失败发生的阶段、结算时记录的原生标识，以及进程退出后引擎记录仍能回答的有界片段；读不到时给出那一个真实原因。原生记录从不复制进 Team、不落盘、不发布；只有发起成员与 Human 能读，其他成员按 `worker_inspect_forbidden` 拒绝。`steer` 用同一个编号加 `instruction`，把这句话补进引擎正在跑的那一个 turn——不开第二个 turn、不排队、不派第二个 Worker——回执只说「已提交」，不说模型读过：接受的含义是引擎把输入接管进了当前 turn，而 turn 若在下一次模型请求前结束，这句话会随之消失。已结束、正在停止、本 Host 不再持有的执行一律拒绝而不是照发，这一版只对 Codex 开放（其他引擎按 `worker_steer_unsupported` 拒绝）；引擎自己拒绝时给出它自己的代码；同一句指令每次执行只送一次：执行仍在跑时和结束后，重送都拿回第一次的回执，用已用过的 request id 送不同指令按 `worker_steer_conflict` 拒绝。只有发起这次执行的成员能补。

只有 Host 的 Worker 实验开关开启时才声明 `team_worker`；关闭后，工具在下一个回合边界收回，不中断已在执行的 Worker。Project owner 的职责与委派判断常驻动态 `team:project-owner` system-prompt section，其中的 Worker 段落在每次组装时读取开关。压缩与换代不会把该 section 丢掉；普通 Session 两者都不会收到。

mention 在 Message 正文里撰写，形如 `@Handle`（`@` 必需、大小写不敏感；规则版本 2 下 `@all` 是普通文本，不通知任何人）；不存在收件人参数。mention 只把这条 Message 送达被点名的 Member 一次，不会使其开始关注。Closed Task 在 Human reopen 前拒绝 reply、Claim 和新的 Attention；taskless Thread 没有 Claim 或 Task resolution mutation path。

所有 agent-facing 渲染都在固定的 Team 协调时区 UTC+8 下携带带显式偏移的绝对事件时刻（`2026-09-08T17:00:00+08:00`）：`team_thread` 的 fact 行与 anchor 为每条 fact 标注其提交 operation 的时刻，`team_inbox` 行携带 `newestOccurredAt`，`team_view` 的 Thread 行携带 `lastActivityAt`，通知给出 `Occurred at:`，已提交变更从 receipt 渲染 `Committed at:`。同一存储时刻在任何重读路径中渲染完全一致；只渲染绝对 timestamp，绝不出现相对时间文案，且 sequence 与 revision——而非 wall-clock 时间——仍是顺序 authority。

Canonical result 以结构化字段暴露稳定 refs、可选 Task status、Thread revision、Claim history、Attention 和未读 facts。[Mutation fences](../../docs/team-collaboration/boundaries.zh.md#mutation-fences) 统一定义令牌来源、完整上下文凭据和拒绝恢复。浏览结果不提供令牌；完整的 `history`/`message` Message 与 Activity 事实可补上下文，但不确认未读。每次写入仍检查新事实、revision、权限和 Task 状态。工具执行通过准确的 live `exec.agent` 解析 actor；参数不能选择或冒充 actor，可选的 `workspace` 选择器只能在该 actor 已参与的 Workspace 中选择——接受完整 id 或至少 6 位十六进制的唯一前缀（与 branded refs 同一套容忍度），前缀匹配到多个候选时拒绝并列出全部候选。写操作的 request identity 由 sessionId 与 tool callId 派生。每个 Team tool 都把结果返回模型循环。

完整的已实现协议见 [`../../docs/team-collaboration/README.md`](../../docs/team-collaboration/README.md)。

## Composition

在 team-enabled Agent preset 内、`dsh-tools` 之后挂载本插件。插件只静态 inject `tools`；执行时从 live Agent context 读取 `agentTeam`，避免 Host 恢复 Member session 时形成依赖环。
