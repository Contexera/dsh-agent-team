# @contexera/dsh-agent-team/tools

English | [中文](README.zh.md)

Model-facing tools for Agent Team Members. The package registers tools in the calling Agent preset scope and does not provide or replace Host services. It carries no context tool: the engine compacts a Member's Session in place and the Host swaps a cold generation, so neither is a model decision.

## Tools

- `team_inbox` lists bounded unread Thread summaries for the calling Member, ordered by direct work and then recency; Task standing appears only where the Thread has a real Task overlay. The header states total unread/direct counts and the number of Threads shown (with a truncation conclusion when unread work lies beyond the bounded list); each item shows its exact unread/direct counts, Project ref, and Task standing. The footer routes reading to `team_thread read`; the render carries no revision and no write token.
- `team_thread` reads a Thread or a Project's Main stream, pages its history, or reads one Message back by ref. `threadRef` is primary; when the Thread has a Task, `taskRef` is an accepted alias for `read`/`history`, while `message` on a Thread requires `threadRef` (any accompanying `taskRef` must identify the same Thread; use `projectRef` for the Main stream). `beforeSequence`/`limit` page history; `read` ignores them and `message` rejects them. The three actions render separately: `read` renders outcome, Thread identity, orientation (the bounded anchor subject when the anchor is not a returned fact), Host-supplied background (not newly acknowledged, and not repeated when already fully visible in the current context), active Claims only, acknowledged Task reminders, the acknowledged facts with inline unread/direct markers (a fully visible body renders `body already in current context; omitted` but still counts as acknowledged; a complete visible Activity renders only its identity marked `complete event already in current context; omitted`), current Task cards as state rather than Thread reading, and a read-through/remaining-unread footer that also states how many Thread facts precede the watermark whenever the read left any behind; `history` renders a historical page with the full anchor on a first page and the bounded subject on continuation pages, never current Claims or a context recommendation; `message` reads one Message back verbatim by ref. `read` advances the durable watermark and is the only read-side source of a next-write token — rendered only when no unread remains; your own committed public mutations hand off a fresh token as well. A read with nothing to acknowledge — nothing unread, or nothing selected within the output ceiling — advances nothing, writes no operation, and renders `Read — no unread updates …` or `Read — no facts acknowledged …`, still answering from the current projection. Activity facts render from the event alone — activity ref, actor, Task and Thread refs, and the Claim refs or transfer endpoints it recorded, never current Task or Claim state. A read that acknowledges an unread acceptance of a still-done Task states that acceptance in its facts and recommends nothing about the reader's context: the model has no context tool and no generation choice. Agent `read` and `message` output is bounded as a whole: the tool selects fewer facts, an oversized Message body returns in ordered character parts, and a read stops before an incomplete Message rather than acknowledging past it. The only continuation is repeating the same request with the same address (and `messageRef`), which resumes at the first missing segment of the current Session surface; there is no offset parameter. An Activity is one line and cannot be split, so one beyond the fixed result ceiling acknowledges nothing, cannot be completed by choosing a larger-context model, and is reported for the Human to inspect directly. A Thread receipt stores the selected bound, while receipts written before it keep the default batch. On the Main stream, read restores the same recent Message background, acknowledges only the selected prefix, and renders Thread cards in their own section without marking those Threads read. Human reads and Remote parameters are unchanged.
- `team_attention` answers only whether you follow a Thread: `status` reports and changes nothing, `follow` and `unfollow` change Attention. All three take one address — a Thread (`threadRef`, or `taskRef` when it has a Task) or the Project Main stream (`projectRef`), never both — plus the routing Workspace, and render one line with the Thread ref, optional Task standing, and following state. Attention is not reading: no action here renders Thread facts, acknowledges unread work, or hands off a write token, and reading a Thread never changes whether you follow it. Your own active Claim on the Thread's Task refuses unfollow until the work is finished or the Claim released.
- `team_message` posts to a Project's Main stream, starts a top-level Thread, or replies to an existing one. `start` takes `kind: 'discussion'` (default) or `kind: 'task'` for atomic Task creation — the removed `asTask` spelling is refused with the parameter route to `kind`, never dropped. A Task start also takes `accountable` (a Project owner's memberRef, or `human`) and `sourceThreadRefs` (the discussion Threads it derives from, whose cards then render there instead of in the Main stream); both are refused on a discussion start and on `post`/`reply` rather than dropped, and a committed start reports the accountable owner it recorded. A committed start/reply renders one committed-verb outcome (Thread created / reply added) with the Message, Thread, and optional Task refs, and exactly one next-write token hand-off. Replies reject unread work before checking token freshness. Typed rejections begin `Not committed`; complete identified Message and Activity facts can supply a token for reconsideration, while partial results route to `read`. Neither result acknowledges unread work. The model-facing result no longer exposes the retired v1 `undeliveredMentions` field; only Host replay reads old receipts.
- `team_dm` sends one private direct message to a single enabled Agent Member in your Workspace. It takes a `memberRef` and a `body` and nothing else — no Thread, no Task, no write token, no attachments — and a stray parameter is refused rather than ignored. The result distinguishes `Delivered` from `Recorded, not delivered` (with the delivery note and a no-blind-duplicate warning); there is no automatic redelivery. The Human cannot be DMed, and mentions in a DM body do not notify anyone else.
- `team_task` reads the Task board through `board`, lists one Task's active Claims through `list`, mutates the calling Member's Direction Claims through `claim`, `done`, and `release`, resolves a Task through `accept`, `close`, `reopen`, and `transfer`, and lets a Project owner promote a discussion Thread into a Task through `promote`; it applies only to real Tasks. `board` shows open Tasks and each Project's newest finished ones, each row naming the accountable owner and, when the reader may verify it, that acceptance is owed; `mine` keeps what the reader is accountable for or executes. `list` renders the Task/Thread identity with active Claims only (the collision surface) and no write token. A committed mutation names its action (Claim created/completed/released, Thread promoted, Task accepted/closed/reopened/transferred), renders the authoritative affected Claim first, and hands off one next-write token. Who may accept, close, reopen, or transfer is the Host's decision, not the tool's: the tool forwards the action and its write token, and a `self_acceptance_forbidden` or `accountable_owner_required` refusal names its way out from the Host's recovery registry and gains the Task's current state and accountable owner, which only the caller can read after the refusal. Rejections share the message rejection form. Direction exclusion uses Unicode NFKC normalization, trim, whitespace compression, and deterministic case folding.
- `team_view` is the address book: bounded, membership-authorized Project, top-level Thread, and Member summaries — current addresses, not a work queue. Threads are the sole paginated catalog: newest-first rows carrying threadRef, Project ref, a bounded anchor subject, and Task standing inline (never a second Task index, never revision or message count). The cursor pages Thread rows only; continuation pages render Threads alone, and paging reaches every authorized top-level Thread, including taskless and off-page taskful ones.


Mentions are authored in the Message body, as `@Handle` (the `@` is required, matching ignores case; `@all` is plain text under rules version 2 and notifies no one); there is no recipient parameter. A mention delivers its Message to the named Member once and never makes them follow. Closed Tasks reject replies, Claims, and new Attention until a Human reopens them; taskless Threads have no Claim or Task-resolution mutation path.

Every agent-facing render carries absolute event instants in the fixed Team coordination zone UTC+8 with an explicit offset (`2026-09-08T17:00:00+08:00`): `team_thread` fact lines and anchors stamp each fact with its committing operation's instant, `team_inbox` rows carry `newestOccurredAt`, `team_view` Thread rows carry `lastActivityAt`, notifications state `Occurred at:`, and committed mutations render `Committed at:` from the receipt. The same stored instant renders byte-identically on every reread path; only absolute timestamps are rendered, never relative text, and sequence and revision — not wall-clock time — remain the ordering authority.

Canonical results expose stable refs, optional Task status, Thread revision, Claim history, Attention, and unread facts as structured fields. [Mutation fences](../../docs/team-collaboration/boundaries.md#mutation-fences) defines token sources, complete-context evidence, and rejection recovery. Browsing results supply no token; complete `history`/`message` Message and Activity facts can supply context without acknowledging unread. Every write still checks new facts, revision, permissions, and Task state. Tool execution resolves the exact live `exec.agent`; arguments cannot select or impersonate the actor, and the optional `workspace` selector can only pick among that actor's participated Workspaces — an exact id or a unique prefix of at least 6 hex characters, the same tolerance the branded refs have, with an ambiguous prefix refused by naming every candidate. Write request identity derives from sessionId plus tool callId. Every Team tool returns to the model loop.

The complete implemented protocol is documented in [`../../docs/team-collaboration/README.md`](../../docs/team-collaboration/README.md).

## Composition

Mount this plugin inside a team-enabled Agent preset after `dsh-tools`. It statically injects only `tools`; execution resolves `agentTeam` from the live Agent context. This avoids a dependency cycle while the Host restores member sessions.
