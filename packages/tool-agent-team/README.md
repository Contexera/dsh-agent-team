# @contexera/dsh-agent-team/tools

English | [中文](README.zh.md)

Model-facing tools for the Agent Team: the Member collaboration surface, plus the read and write tools the Host-owned Team manager Session uses. The package registers tools in the calling Agent preset scope and does not provide or replace Host services. It carries no context tool: the engine compacts a Member's Session in place and the Host swaps a cold generation, so neither is a model decision.

## Tools

- `team_inbox` lists bounded unread Thread summaries for the calling Member, ordered by direct work and then recency; Task standing appears only where the Thread has a real Task overlay. The header states total unread/direct counts and the number of Threads shown (with a truncation conclusion when unread work lies beyond the bounded list); each item shows its exact unread/direct counts, Project ref, and Task standing. The footer routes reading to `team_thread read`; the render carries no revision and no write token.
- `team_thread` reads a Thread or a Project's Main stream, pages its history, or reads one Message back by ref. `threadRef` is primary; when the Thread has a Task, `taskRef` is an accepted alias for `read`/`history`, while `message` on a Thread requires `threadRef` (any accompanying `taskRef` must identify the same Thread; use `projectRef` for the Main stream). `beforeSequence`/`limit` page history; `read` ignores them and `message` rejects them. The three actions render separately: `read` renders outcome, Thread identity, orientation (the bounded anchor subject when the anchor is not a returned fact), Host-supplied background (not newly acknowledged, and not repeated when already fully visible in the current context), active Claims only, acknowledged Task reminders, the acknowledged facts with inline unread/direct markers (a fully visible body renders `body already in current context; omitted` but still counts as acknowledged; a complete visible Activity renders only its identity marked `complete event already in current context; omitted`), current Task cards as state rather than Thread reading, and a read-through/remaining-unread footer that also states how many Thread facts precede the watermark whenever the read left any behind; `history` renders a historical page with the full anchor on a first page and the bounded subject on continuation pages, never current Claims or a context recommendation; `message` reads one Message back verbatim by ref. `read` advances the durable watermark and is the only read-side source of a next-write token — rendered only when no unread remains; your own committed public mutations hand off a fresh token as well. A read with no fact or reminder to acknowledge advances nothing and writes no operation. A reminder-only read still confirms its reminders and reports a commit. With nothing acknowledged, the result says `Read — no unread updates …` if nothing remains, otherwise `Read — no facts acknowledged …`; the picture comes from the current projection. Activity facts render from the event alone — activity ref, actor, Task and Thread refs, and the Claim refs or transfer endpoints it recorded, never current Task or Claim state. A read that acknowledges an unread acceptance of a still-done Task states that acceptance in its facts and recommends nothing about the reader's context: the model has no context tool and no generation choice. Agent `read` and `message` output is bounded as a whole: the tool selects fewer facts, an oversized Message body returns in ordered character parts, and a read stops before an incomplete Message rather than acknowledging past it. The only continuation is repeating the same request with the same address (and `messageRef`), which resumes at the first missing segment of the current Session surface; there is no offset parameter. An Activity is one line and cannot be split, so one beyond the fixed result ceiling acknowledges nothing, cannot be completed by choosing a larger-context model, and is reported for the Human to inspect directly. A Thread receipt stores the selected bound, while receipts written before it keep the default batch. On the Main stream, read restores the same recent Message background, acknowledges only the selected prefix, and renders Thread cards in their own section without marking those Threads read. Human reads and Remote parameters are unchanged.
- `team_attention` answers only whether you follow a Thread: `status` reports and changes nothing, `follow` and `unfollow` change Attention. All three take one address — a Thread (`threadRef`, or `taskRef` when it has a Task) or the Project Main stream (`projectRef`), never both — plus the routing Workspace, and render one line with the Thread ref, optional Task standing, and following state. Attention is not reading: no action here renders Thread facts, acknowledges unread work, or hands off a write token, and reading a Thread never changes whether you follow it. Your own active Claim on the Thread's Task refuses unfollow until the work is finished or the Claim released.
- `team_message` posts to a Project's Main stream, starts a top-level Thread, or replies to an existing one. `start` takes `kind: 'discussion'` (default) or `kind: 'task'` for atomic Task creation — the removed `asTask` spelling is refused with the parameter route to `kind`, never dropped. A Task start also takes `accountable` (a Project owner's memberRef, or `human`) and `sourceThreadRefs` (the discussion Threads it derives from, whose cards then render there instead of in the Main stream); both are refused on a discussion start and on `post`/`reply` rather than dropped, and a committed start reports the accountable owner it recorded. A committed start/reply renders one committed-verb outcome (Thread created / reply added) with the Message, Thread, and optional Task refs, and exactly one next-write token hand-off. Replies reject unread work before checking token freshness. Typed rejections begin `Not committed`; complete identified Message and Activity facts can supply a token for reconsideration, while partial results route to `read`. Neither result acknowledges unread work. The model-facing result no longer exposes the retired v1 `undeliveredMentions` field; only Host replay reads old receipts.
- `team_dm` sends one private direct message to a single enabled Agent Member in your Workspace. It takes a `memberRef` and a `body` and nothing else — no Thread, no Task, no write token, no attachments — and a stray parameter is refused rather than ignored. The result distinguishes `Delivered` from `Recorded, not delivered` (with the delivery note and a no-blind-duplicate warning); there is no automatic redelivery. The Human cannot be DMed, and mentions in a DM body do not notify anyone else.
- `team_reminder` creates, lists, or cancels a reminder for yourself: a time promise bound to you as a Member rather than to a Session. `create` takes `scheduleKind` with that kind's own fields (`once` + `at`, `every` + `minutes` of at least 10, or `cron` + a five-field `expression` read in the fixed UTC+8 zone) and always `note`, at most 2000 characters. At most 50 reminders stay active for you, and a schedule named without its own field is refused rather than guessed. `list` reports every reminder you own with its state and occurrence facts; `cancel` withdraws one by `reminderRef`. A due occurrence reaches your Team Inbox as a private notice and wakes you, the Host records it consumed once it enters one of your turns, and a missed one is made up once after recovery. While you are suspended your reminders keep timing; archiving or removing you cancels them. Only you create your own; the Human withdraws from Member detail.
- `team_subscription` creates, lists, changes, tests, pauses, resumes, deletes, re-baselines, and replays one failed delivery of a Project's script subscription. Any Member may `list` and read `logs`; only Project owners may write. Create and update snapshot the script (at most 16 KiB), run it once, and refuse the write when that trial fails; the Host deduplicates the JSON-lines events a script prints and publishes at most 20 per minute. `logs` renders the newest runs with revision, trigger, category and event count, while owners and the Human also see failure reasons and output tails. `deliveries` lists webhook requests whose automatic retries were spent, and `replay` reruns one under either the current definition or the one it arrived under. Create, update and `reset_webhook` can arm a webhook address, returned exactly once because the Host stores only its hash; a retried call with the same request id still checks current Project ownership, answers from the ledger without reading script files or credentials, and says whether the address can no longer be fetched. A legacy create or update without a stored script path refuses that path retry with the committed subscription ref.
- `team_task` reads the Task board through `board`, lists one Task's active Claims through `list`, mutates the calling Member's Direction Claims through `claim`, `done`, and `release`, resolves a Task through `accept`, `close`, `reopen`, and `transfer`, and lets a Project owner promote a discussion Thread into a Task through `promote`; it applies only to real Tasks. `board` shows open Tasks and each Project's newest finished ones, each row naming the accountable owner and, when the reader may verify it, that acceptance is owed; `mine` keeps what the reader is accountable for or executes. `list` renders the Task/Thread identity with active Claims only (the collision surface) and no write token. A committed mutation names its action (Claim created/completed/released, Thread promoted, Task accepted/closed/reopened/transferred), renders the authoritative affected Claim first, and hands off one next-write token. Who may accept, close, reopen, or transfer is the Host's decision, not the tool's: the tool forwards the action and its write token, and a `self_acceptance_forbidden` or `accountable_owner_required` refusal names its way out from the Host's recovery registry and gains the Task's current state and accountable owner, which only the caller can read after the refusal. Rejections share the message rejection form. Direction exclusion uses Unicode NFKC normalization, trim, whitespace compression, and deterministic case folding.
- `team_view` is the address book: bounded, membership-authorized Project, top-level Thread, and Member summaries — current addresses, not a work queue. From rules version 8 a Project row also states what its Agent owners answer for there, reading a grant that records none as `unspecified`; a Project where nobody recorded one adds nothing. Threads are the sole paginated catalog: newest-first rows carrying threadRef, Project ref, a bounded anchor subject, and Task standing inline (never a second Task index, never revision or message count). The cursor pages Thread rows only; continuation pages render Threads alone, and paging reaches every authorized top-level Thread, including taskless and off-page taskful ones.
- `team_worker` delegates one self-contained piece of work to a local Worker engine (Codex or Claude Code) that runs with its own tools, login, and settings, stops one execution, steers its native session, or reads one execution's diagnostic. A delegation names a Thread, Task, or Project; the target decides where the run reports — a bound run publishes its start and ending to the Thread and answers in the delegating Member's Inbox, while a Project-only run publishes nothing and answers in the caller's session. The call returns once the execution is accepted; there is nothing to poll. `stop` takes one `worker:` ref this session delegated and waits for the engine to confirm its cleanup, bounded: past the deadline the run stays `running` and is refused as `worker_stop_pending`, and an engine that reports a failed teardown records `failed` with an unconfirmed-cleanup diagnostic rather than `stopped`. `inspect` takes the same ref and answers the summary the Thread already carries, the stage a failed run came apart in, the native identities and owned turns the settlement recorded, and the bounded fragments the engine's own record still answers after the process exited — or the one reason it cannot. The native record is never copied into the Team, never stored, and never published; only the initiating Member and the Human may read it, and another Member is refused as `worker_inspect_forbidden`. `steer` takes the same ref with `instruction`; Codex and Claude both deliver it into the same native session, where OAR may use the current turn, a queued turn, or an idle session's next turn. An execution waits for every accepted input, so its later answer, failure, stop, timeout, and partial output stay in the same Team ending. The receipt says submitted or continuation started, never that the model read it or that it landed in a fixed turn. If the latest linked execution ended cleanly, including a clean failure, steer resumes its native session as a new linked execution and returns the new `worker:` ref plus `continuedFrom`; the old ending is unchanged and the new ref can be steered, stopped, or inspected again. A failed continuation that opened no native session may inherit the nearest readable predecessor anchor on a later explicit attempt while remaining the direct predecessor. Stopping, unconfirmed cleanup, an archived Project, lost owner or Member permission, a disabled engine or Worker switch, a missing or mismatched native record, and a previous-Host running record are refused. One request id is idempotent; within one execution, the same sentence is deduplicated while pending, submitted, or transport-ambiguous, while an explicit native refusal or a later linked execution may use the text under a fresh id. Only the Member who delegated the original execution may steer it.

`team_worker` is declared only while the Host's experimental Worker switch is enabled; disabling it withdraws the tool at the next turn boundary without disturbing a run already in flight. Project-owner responsibilities and delegation judgment live in a dynamic `team:project-owner` system-prompt section, whose Worker paragraph follows the switch at each assembly. Compaction and generation swaps do not discard that section. Ordinary Sessions receive neither.

- `team_overview` reads the whole Agent Team as the Team manager, read-only: every Workspace in the Host directory with its checkout path, every Project with its shared goal, its owners and what each answers for, its live subscription counts and board summary, and every Member with where it participates, how it runs, and what it owns. It carries no message body, Thread fact, credential, or private file content. It narrows by `workspaceId`, `projectRef`, or `memberRef`; a `memberRef` read adds that Member's private directory path and nothing beyond it. Each collection is bounded by `limit` and a cut collection says so through `truncated`, so a large Team is paged by scope instead of silently shortened. An empty answer means the Team is empty, while an unknown `workspaceId` or `projectRef` is refused rather than answered as empty. The same handle in two Workspaces is two Members, so one is addressed by its `memberRef`; an owner whose grant recorded no responsibility reads `unspecified`, a Project whose only owner is the Human is a fact rather than a fault, and a long-standing Member with no owner relation is reported the same way. Full Thread and Task detail stays with `team_thread` and `team_task`.
- `team_models` lists the model routes a Team Member may run: every provider group with its models, each model's reasoning efforts, the deployment default, and the providers whose catalog lookup failed. It reads the Session controller's own catalog rather than restating it, so a route named here is selectable in the Web member editor, and a provider whose lookup failed is reported in `failures` and never folded into an empty list. `memberPresets` names the one preset a Member may compose; the manager's own preset is Host-owned and never member-selectable, so it never appears there.

- `member_create` creates one Agent Member in one Workspace as the Team manager. The write rides the Host's own addition path — the same serialized queue, activation and receipt the Web Client uses — so the record it answers with is the record every other surface reads. It takes the handle (free in that Workspace), a non-empty description of the Member's global standing, an explicit model route exactly as `team_models` listed it, and optional capability intent whose absence means the full standard surface. The Member is addressed from now on by its `memberRef`, never by its handle, because the same handle in two Workspaces is two different Members.
- `project_create` creates one Project in an existing Workspace as the Team manager, recording its shared goal as the description. Only Members that are already active in this Workspace may join at creation — the Host's own admission rule, stricter than the ledger's — so a Member whose activation failed is refused here with its reason: create the Project without it, or fix that Member first. An empty shared goal is refused, because a Project exists for a continuing result someone answers for. Omit `memberIds` to create the Project empty and grant owners afterwards.
- `member_update` edits one existing Agent Member's mutable facts as the Team manager: its description, its model route, and its capability configuration. It is a partial update — every field the call leaves out keeps the value stored at the moment the write runs, merged inside the ledger's serialized section, so an edit cannot overwrite a rename or description change that landed while it was queued, and a replayed `requestId` compares only the fields it stated. The handle and the preset are not editable here. An explicit blank description is refused, because a Member is addressed by what it is for. An omitted `capabilities` keeps the stored override while `clearCapabilities: true` restores the full standard surface; the two are refused together, because clearing is not the same as setting an empty list. A replacement route is checked against the same catalog `team_models` lists, and only while the request is new. The answer keeps the durable receipt and reports how far the stored configuration reached the live runtime — `applied`, `already-applied`, `deferred:no-live-handle`, `deferred:generation-changed`, or `failed:model-apply` / `failed:capability-apply` with the Member's own diagnostic — so a committed write whose live apply failed is never answered as an uncommitted rejection. The failing stage names the effect, and the comparison is against what the live generation runs: replaying the same request retries the effect still owed, while a route a later edit replaced is never put back.
- `member_state` changes one Agent Member's lifecycle as the Team manager. `suspend` and `resume` are the Host's existing durable operations: a suspended Member keeps its Session and private data, and resume activates it again. `archive` hides the Member everywhere, releases its active Claims, clears its Attention, and keeps its private memory and Session log on disk; this version has no permanent-removal tool, and archived is the end state it offers. `recover` is a runtime-only repair with no ledger record: it finishes an interrupted generation swap or suspend cleanup, rebuilds a Member whose preset composition was orphaned by a reload, or restarts one whose activation failed. It needs the Workspace id whose participation the Host verifies, and it refuses a Member that is not enabled when a restart is the only path. A refusal names its reason and writes nothing; a committed write answers its receipt and the Member's standing after it.
- `member_workspace` changes one Agent Member's Workspace participation as the Team manager. `join` grants participation in another Workspace as a pure relation — the Member's Session is not created, copied, or moved, and it keeps working from its original checkout. `leave` withdraws one non-default Workspace: its active Claims there release, its Attention and markers on those Threads clear, and its Project memberships there end, while identity, Session, and remaining participations stay. The creation Workspace cannot be left — archive the Member instead.
- `project_owner` changes one Agent Member's ownership of one Project as the Team manager. `add` grants it and records the responsibility the Member answers for there; `update` replaces that responsibility without withdrawing and re-granting, so the Member keeps its grant, its Main stream Attention and its history across the change; `remove` withdraws the relation. The grantee must already participate in the Project's Workspace and be enabled or suspended — an archived Member is refused with its reason — and the grant itself is that Member's Project participation. The responsibility is a bounded statement distinct from the Member's global description and the Project's shared goal: `add` refuses an empty one, and `update` accepts an explicit empty one (or `clearResponsibility: true`) to record `unspecified`, which is a fact about the grant rather than a gap to repair. A duplicate grant is refused rather than silently kept. Withdrawal ends the relation only: a Member that still takes part in the Project keeps the Tasks it is accountable for, and one whose participation ends hands them back to the Human.
- `project_update` edits one Project or archives it as the Team manager. `update` changes the name, the shared goal, or both, and it is a partial update: a field the call leaves out keeps the value stored at the moment the write runs, merged inside the ledger's serialized section, so a rename cannot write back a goal the Human changed while it was queued. An explicit empty goal clears it the way the Web editor does; an empty name is refused. `archive` is the Project's end state: every fact and the whole history stay readable, its active Claims release, the related Attention clears, and every subscription it owns stops and loses its private state. A cleanup that fails after the archival commits is named in the answer as a warning beside the receipt, so the durable decision is never answered as an uncommitted rejection.

Each write carries a `requestId`: pass your own when the write matters enough to retry, and the same id with the same parameters answers with the original receipt instead of writing twice, while a changed parameter under a reused id is refused as a collision. A refusal names its reason and wrote nothing. A committed Member whose activation failed is still committed: the answer keeps its receipt, ref and activation diagnostic, so continue from there instead of creating it again.

`team_overview`, `team_models`, `member_create`, `project_create`, `project_owner`, `project_update`, `member_update`, `member_state` and `member_workspace` serve the Host-owned Team manager Session, not a Member: the `team-member` preset does not declare them, and each handler refuses any Session that is not the current manager Agent. `ownsSession` cannot authorize that call, because it answers lineage and a replaced manager generation still satisfies it. A write authorizes twice — the same manager gate at the tool, and the ledger's own authorize hook inside the serialized section after the idempotency replay branch resolves — so a manager replaced between its call and its commit is refused with nothing written.

Mentions are authored in the Message body, as `@Handle` (the `@` is required, matching ignores case; `@all` is plain text under rules version 2 and notifies no one); there is no recipient parameter. A mention delivers its Message to the named Member once and never makes them follow. Closed Tasks reject replies and Claims until a Human reopens them, while following their Thread still starts Attention; taskless Threads have no Claim or Task-resolution mutation path.

Every agent-facing render carries absolute event instants in the fixed Team coordination zone UTC+8 with an explicit offset (`2026-09-08T17:00:00+08:00`): `team_thread` fact lines and anchors stamp each fact with its committing operation's instant, `team_inbox` rows carry `newestOccurredAt`, `team_view` Thread rows carry `lastActivityAt`, notifications state `Occurred at:`, and committed mutations render `Committed at:` from the receipt. The same stored instant renders byte-identically on every reread path; only absolute timestamps are rendered, never relative text, and sequence and revision — not wall-clock time — remain the ordering authority.

Canonical results expose stable refs, optional Task status, Thread revision, Claim history, Attention, and unread facts as structured fields. [Mutation fences](../../docs/team-collaboration/boundaries.md#mutation-fences) defines token sources, complete-context evidence, and rejection recovery. Browsing results supply no token; complete `history`/`message` Message and Activity facts can supply context without acknowledging unread. Every write still checks new facts, revision, permissions, and Task state. Tool execution resolves the exact live `exec.agent`; arguments cannot select or impersonate the actor, and the optional `workspace` selector can only pick among that actor's participated Workspaces — an exact id or a unique prefix of at least 6 hex characters, the same tolerance the branded refs have, with an ambiguous prefix refused by naming every candidate. Write request identity derives from sessionId plus tool callId. Every Team tool returns to the model loop.

Optional-slot compatibility is action-specific: meaningless placeholders are normalized without erasing real content, clearing instructions, or conflicts. The [tool protocol](../../docs/team-collaboration/tools.md#optional-argument-slots) defines the boundaries; the schema-driven matrix checks every registered tool rather than a fixed list of older tools.

The complete implemented protocol is documented in [`../../docs/team-collaboration/README.md`](../../docs/team-collaboration/README.md).

## Composition

Mount this plugin inside a team-enabled Agent preset after `dsh-tools`. It statically injects only `tools`; execution resolves `agentTeam` from the live Agent context. This avoids a dependency cycle while the Host restores member sessions.

Each preset names the exact tools it mounts through the plugin's `only` config, because the model's visible tool list is read from the registering scope's own schemas: a tool registered here and hidden later is still listed to the model, and a tool refused in its handler is still spent on before it fails. `team-member` names the ten Member tools; `team-manager` names the nine manager tools — `team_overview`, `team_models`, `member_create`, `project_create`, `project_owner`, `project_update`, `member_update`, `member_state` and `member_workspace` — and nothing else. Omitting `only` registers every tool this package defines, and an unknown name in the list is refused rather than skipped, so a typo cannot mount an empty surface that only surfaces as a Session that cannot act.
