# 需求决策快照 — Thread 消息回复（引用回复）

## 1. 需求

在 Thread 时间线里选中某一条消息，对它做「回复」：回复消息本身携带对原文的引用，读者能看出「这条是在回哪一句」，并能跳回原文。

## 2. 已确认的约束

- **仅 Thread 页**。Channel 顶层 feed 不在本次范围（与气泡功能保持同一范围决策）。
- 交互必须**键盘可达**：不能只有 hover 才能操作。
- 引用的可见形态必须能表达「原文很长」，不能把整段原文再贴一遍。

## 3. 已勘察的事实

| 项 | 结论 |
| --- | --- |
| `AgentTeamMessage` 是否有父消息字段 | **没有**，需要新增 |
| ledger 是否 append-only | 是；新增字段必须可选且 replay 可归一化 |
| 是否已有引用渲染 | 有 `task:` / `thread:` / `channel:` / `member:` branded ref 的 chip 渲染可复用 |
| shipped 的消息操作条约定 | `data-actions-reveal="hover"` + `opacity: 0→1`（80ms），整体包在 `@media (hover: hover)` 内，触屏常显 |

## 4. 原型中的设计选择（待确认）

| # | 选择 | 理由 |
| --- | --- | --- |
| R1 | 引用块渲染在气泡**内部顶部**，正文在其下方 | 与「有人@我」标记同一位置层级；读者先看到「在回哪句」再读正文 |
| R2 | 引用块是**一行截断**（作者 + 摘要），点击跳到原文并短暂高亮 | 长原文不能重贴；跳转比展开更符合「引用」语义 |
| R3 | 回复中的原消息加**描边高亮** | 让「我在回这条」有明确落点，而不是只靠 composer 里的文字 |
| R4 | composer 顶部出现**引用条**（作者 + 摘要 + 取消） | 与 composer 卡片同一表面；取消必须显眼 |
| R5 | 操作条复用 shipped 约定：`@media (hover: hover)` 内才隐藏，触屏常显 | 触屏没有 hover，隐藏等于不可用 |

## 5. 未决项（需要你裁决）

### O1 — Channel 页要不要也能回复

三个选项：

- **A**：Thread 页独有（当前原型）。
- **B**：Channel 顶层消息上的「回复」= **进入该消息的 Thread 并在 composer 预置引用**。ledger 模型不变。
- **C**：Channel 里也允许顶层消息引用顶层消息。需要新的顶层消息父子关系，改动面最大。

### O2 — 回复是否自动通知原文作者

现在只有 mention 会通知。回复是否等价于一次「指向性的送达」：

- **A**：不通知，纯引用。要通知就自己写 `@作者`。
- **B**：回复自动把原作者加入收件人（等价于隐式 mention）。

### O3 — 引用存 messageRef 还是同时存正文快照

- **A**：只存 `replyToMessageRef`，渲染时由 Host 解析作者与摘要。原文永远在 ledger 里，不会丢。
- **B**：同时存一段快照正文，即使原文读不到也能显示。

A 更干净（单一权威）；风险是「原文不在当前加载窗口」时需要 Host 解析或退化为不可点。

### O4 — 引用块的视觉形态

当前原型用「左侧竖线 + 淡底」。要确认是否与刚统一的「不用左侧强调条」原则冲突 —— 「有人@我」已改为描边 + 徽标，而引用块是**引用语义**（业界惯例就是竖线）。可选：

- **A**：左侧竖线 + 淡底（当前原型，引用惯例）
- **B**：只有淡底、无竖线
- **C**：只有一行文字（作者 + 摘要）+ 下划线，最轻
