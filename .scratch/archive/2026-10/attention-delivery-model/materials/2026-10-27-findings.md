# 调研证据：attention 与投递的现状

日期：2026-10-27。全部结论经代码阅读 + 临时测试实测确认（测试未入库）。

## 1. 缺口实测

场景：一个 Agent owner 在 Project 内，另一个普通 member 在 Task Thread 里发消息。

| 操作序列 | owner 收到的通知数 |
|---|---|
| owner 自己开 Task（accountable=自己）→ 自己 claim → 别人连发 4 条不点名 | **0** |
| 同上，第 5 条 | 1（threshold 摘要） |
| Task 进入 in_review → 别人发 1 条 | **0** |
| 同上，累计 4 条 | **0** |
| 同上，第 5 条 | 1 |
| 同一条消息改成 @owner | 1（immediate） |
| owner 主动 unfollow 后，5 条 | 0 |

对照：Task 状态跃迁本身全部有 immediate 通知（claim → in_progress 1 次，done → in_review 1 次）。

结论：**跃迁通知得到，过程消息全沉底**。而 in_review 恰好是 accountable 最需要盯的阶段（它是验收人）。

## 2. 根因

`packages/agent-team/src/inbox-delivery.ts` 的判定函数只接受一个 owner 布尔：

```
owner && message && !direct  →  threshold
其它                          →  immediate
```

`owner` 的来源是 `projectOwnerIds(projectRef).includes(memberId)`，纯粹是 Project 身份。**attention 状态完全不参与投递等级计算。**

## 3. follow 对 owner 无效的实证

同一 Project 放两个 Agent owner，一个开 Thread（自动 follow），一个从不 follow，第三人发 5 条消息：

| owner | 是否 follow | 通知数 |
|---|---|---|
| 开 Thread 的 | 是（自动） | 1（threshold） |
| 旁观的 | 否 | **0** |

再把「建 Task 时自动 follow 的 accountable」单独测：它确实已被自动 follow，5 条普通消息后仍只拿到 1 次 threshold。

所以：**follow 只决定有没有未读，不决定多快被通知。** 这正是「看不出 follow/unfollow 有什么作用」的来源。

## 4. 已有的自动 follow 点（durable 责任信号上）

| 触发 | 位置 |
|---|---|
| Thread 作者 | ledger.ts:1377 |
| Task accountable（建 Task 时） | ledger.ts:4760 |
| Claim executor | ledger.ts:1511 |
| reopen 时恢复 accountable 的 follow（`refollowedMembers`） | ledger.ts:1625 |
| close 时收回全部 attention | ledger.ts:4398 |
| transfer 时新 accountable follow，旧的不收回 | ledger.ts:1552 |

这些已经构成「责任 → attention」的映射，缺的只是「attention → 投递」。

## 5. 两套平行的未读派生机制

- Thread 侧：`attention` + `startSequence`/`readThroughSequence` 水位。
- Main stream 侧：`ownerSinceFrom`（授权序列号）+ `mainWatermarks`，见 ledger.ts:4808。owner 身份直接派生未读，不经 attention。

spec §7 的投递表对 Main stream 也是「owner → immediate」。

## 6. 结构缺陷的补偿补丁

`affectedMembersOf`（ledger.ts:2670）有一段 owner fan-out，注释自陈：「Without this the wake only follows inbox deltas, so an owner's derived unread grows with no commit ever notifying them.」——它在补偿「owner 没有 attention 所以收不到唤醒」。若改 attention-only，这段可删。

## 7. 上位设计的自相矛盾处

`project-ownership-model/spec.md` §1 概念表：Thread Attention 回答「谁收到某个 Thread 的普通更新」。
同一份 spec §7 投递表：Thread 普通消息，recipient 是 owner 或 accountable → threshold（无视 Attention）。

spec §6.1 还写明「accountable owner 自动 follow Task Thread，但普通消息对它按 threshold 投递」——自动 follow 了一个它并不按 follower 待遇对待的 Thread。

`materials/2026-10-22-inbox-delivery-model.md` §2.1 曾列出 `recipient role` 与 `delivery class` 两个独立字段，其中 role 含 owner/accountable/follower/claim executor/direct target。**role 决定 class 就是当前矛盾的来源**；该文也承认「Owner 被撤销、Task 转交、Member 状态变化后，同一个未读事实可能需要重新计算投递政策」——即 role 派生本身不稳定。

## 8. 已取消但被重新提及的层

`materials/2026-10-22-inbox-delivery-model.md` §4 设计过 Thread participant grant（协作资格，grantedBy reason: creator/follow/claim/accountable/message-author），spec §12 已撤回，理由是「自助 follow 之后这道门不保护任何东西」。本轮讨论中 Human 提到 participant 与 follow 分离，需确认是否指恢复该层——初步判断不是：本轮要解决的是投递，不是协作资格。

## 9. threshold 的运行时局限（已知，非本轮引入）

`summarizedThrough` 与 `covered` 签名只存进程内存（index.ts 注释已声明）。Host 重启会集中补发，保证 at-least-once 而非 durable 记录。这是既有限制，与投递判据的改变独立。
