# Channel 页分流：已确认的决策快照

本文件是讨论收敛后 Human 拍板的结论，**是决策记录，不是 API 权威**——当前行为以 `packages/` 源码、测试与 `docs/frontend-design/` 双语对为准。工单见 [`issues/`](issues/)。

## 1. 分流：按时间形状分两类

Channel 时间线上有两种东西，混在一起时看不出「什么还在动」——现状截图里五个已完成 Task 与进行中的 Task 同样体积，流变成坟场。对策不只是换样式，而是承认两者是**两种读法**：

| | 入口 | 落在哪 |
| --- | --- | --- |
| Task（低频、进入即验收、要宽） | 入口行 | 既有 Thread 页层级（`selectThread`），**不另开窗口** |
| 无 Task 的讨论（跨天、低强度、要 channel 上下文常在视野） | 入口行 | Channel 页右侧面板，feed 仍在旁边 |

**不要 task 弹窗。** 早期草图（v1 `prototype.html`）给 Task 做了居中弹窗；v2 改掉：Thread 页已经承载 Claims 与验收，弹窗会让同一个 Task 有两个面。

## 2. 看板入口：页签，不是按钮

「频道 | 看板」做成页头下栏的页签行，压在自己的收口线上，说 shipped 主产品 session 页「对话 | 轨迹」的语言。不做右上角按钮——这是两种读法的切换，不是一次动作。

看板四列（待处理 / 进行中 / 待验收 / 已完成）折叠五种 Task 状态（`done` 与 `closed` 共用已完成的列）。已完成的卡片降透明度而不隐藏：看板的工作是让在动的最响，同时让做完的还能找到。

## 3. 布局：一个数字决定面板开时 feed 会不会重排

feed 正文列是 `margin: 0 auto; max-width: 880px`（居中）。实测三种模式在**面板关闭 → 打开**时主列的行为：

| 模式 | 列宽变化 | 左缘位移 | 后果 |
|---|---|---|---|
| `center`（当时的现状） | 880 → 608（**Δ272**） | **Δ44** | 整列重排，**每一行文字重新折行** |
| `left`（「消息靠左」的提议） | 880 → 608（**Δ272**） | 0 | 左缘不动，**仍会折行** |
| `reserve`（预留面板位） | 608 → 608（**Δ0**） | 0 | **不折行** |

**结论：光靠左不解决折行，只有预留宽度才解决。** 实测环境：1440 / 1680 / 1920 三种视口，居中列两侧各留 101.5 / 221.5 / 341.5px 空档。

**实施时改为「仅打开时预留」**（偏离上表的常驻 reserve）：常驻预留的代价是面板未开时也常驻一条空带，1440 视口下 feed 每一行都为它付费。改为开关时重排一次，而那正是读者注意力已经移向面板的时刻。上表的 608px 数字不再适用。

**页头不属于这条列。** 页头是面板 chrome，贴面板左缘约 28px；正文列仍居中。shipped 会话页自己就是 `padding: 10px 28px 0 20px` 贴左、正文 inset 198px——**标题与正文刻意不在同一个 x 上**，Team 页面照搬这个安排。

## 4. 移动端

600px 以下（代码库既有断点）面板覆盖整个 stage，而不是挤在一条读不下去的 feed 旁边。草图里的抽屉形态（78% 高度 + 遮罩）未采用。
