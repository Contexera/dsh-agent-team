Context 管理：三个动作与一个状态面

模型管理 context 只有三个动作：压缩、换代、回退。今天只有一个入口能用——换代。压缩没有模型入口，回退有入口却被描述挡在门外。三个动作共享同一个结构：锚点。所以它们不是三件事，是一件事的三个方向。本设计补两件东西：一个状态面（发现入口），一个压缩动作（执行机构）。

1今天的四个动作

压缩compact模型没有这个动作 —— compaction 只有人类斜杠命令 /compact（走 compactNow）
换代rollover能用：context_rollover —— 写 handoff → 新 Session → 重新装配
回退return有入口（context_rollover + checkpointRef），但描述写着"只在已经想回退时用"
看状态status有：context_timeline —— 但它只答"谱系里有哪些点"，不答"我在哪、能做什么、代价多少"

已核验：/compact 是斜杠命令（人类敲的，经 runMaintenance 要求 true idle）；模型可调的 context 工具只有 context_rollover / context_checkpoint / context_timeline 三个。

后果：Team 在验收读到 128K 时建议换代——此刻离 handoffAt（默认 200K）还有七万多 token 余量，却要求最贵的那个动作。
实测（先测后写）：我在自己的 Member 会话里调了 context_timeline —— 8 行里 5 行可回退，每行都只属一个 Thread。回退能力在，只是没人用：描述把它挡在门外了。

2四个对象 · 三个动作 · 一个状态面

四个对象

工作集模型现在看得到的东西。它的 token 数就是"用了多少"
日志落盘的完整记录。只追加。工作集是它的一种投影
锚点谱系里一个可寻址的位置
代一次上下文代。换代就是结束一代、开始新一代

三个动作 + 看状态

动作代代价
压缩同一代一次摘要调用；cache 前缀可能失效
换代新一代写 handoff；重新装配；cache 重热
回退新一代丢掉锚点之后的内容；cache 重热
看状态同一代几乎为零
方向不同，这是关键。压缩是"身后太长，缩短它"；换代是"翻到新的一页"；回退是"翻回旧的一页"。三者都不删日志——被压掉的、被丢掉的，都还在日志里。

3锚点是共同货币

三种位置标记是同一类结构：谱系里的一个点。差别只在来源与用途。

压缩指令标出的位置

"这条之前是旧的。"

来源：模型这一次的调用。用途：划定可压区间。

今天指令不是 timeline 里的一行。

Team 边界自动标出的位置

team_message / team_claim / attention 变更都会自动产生。

来源：账本里的操作。用途：回退的候选点。

今天它们是 timeline 里的行。

缺口就是这个：今天的 timeline 行只有 checkpoint / boundary / handoff / head 四种，压缩指令不在其中。模型手里能看见的位置，与它能压缩的位置，是两个不相干的集合。

同一个工具改名换描述：context_timeline → context_status。不新开工具——锚点行就是回退的决策面，状态面是它的超集。数据取自一次真实会话。

锚点行原样保留 retained / discarded / restorable / 理由——那几行就是回退的决策面。

三点说明：① 组成只有三类（system / tools / messages），不是按 Thread——按 Thread 的数字只在锚点行里有；toolsTokens 是工具 schema，不是工具结果，工具结果算在 messages 里。② "现在能压多少"是算出来的（用量 − 保留尾），不是存储字段。③ 人类界面已经有这个组成（Web 端 ContextMeter 的环），模型看不到。

模型定时机；压哪一段由宿主选出，引擎校验（配平、存在、稳定性）。模型不碰 seq。第一版工具不带参数。

同一个 Session。摘要事务、平衡边界校验、token 计量全部复用 DSH 既有实现。

失败方向全都倒向"不压"：没有可压区间、边界不合法、generation 已变化、摘要或事务失败、取消——一律保留原 surface 并如实回报。不静默，不谎报成功。模型调用时机不对，代价只是多一次摘要调用，不是丢事实。

6契约：区间不含指令及其后

今天为什么成立 —— 但是副作用

保留尾默认是窗口的 0.16（200K 约 32K）。一条指令消息只有几十 token，必然落在保留尾里。所以区间自然停在指令之前。

没有人保证它。它是保留尾预算的副产品。

两处会破

① retainTokens = 0——overflow 那条路就是这么调的。区间末端正好落在"最新节点之前的那一条"上，就是指令那条：指令把自己压掉。

② 将来有人调小保留尾。静默失效，没有测试看着它。

做法（已定，选项 B）：上界由我们给——区间上界卡在"最新那条 user/message 之前"。门控触发时它正好是压缩指令；模型自判时它等于"本轮整段原样保留"，比保留尾 32K 更保守。加测试。一个会删内容的机制，边界值得是契约。

7两条流程

A — 模型自判

1模型在边界处调状态面（刚闭合一段、长间隔回来、不确定站在哪里）
2模型看到用量、组成、可压量、锚点
3模型决定：压缩 / 回退 / 什么都不做

这条不需要宿主参与。它今天就能成立——只差工具描述别再挡门。

B — 长间隔相关性门控

1宿主pre-step 读用量与间隔：≥ 128K 且 距上一 turn ≥ 30min
2jev问一次：本次输入与最近几轮 user_input 有关吗
3宿主有关 / 判不出 / jev 不可用 → 不压，正常继续
4宿主无关 → 扣住本次输入，reject 这一步
5宿主followup 投一条压缩指令。它成为最新 user_input
6模型调用压缩动作。区间只覆盖指令之前的内容
7宿主压完 → 把扣住的输入投回去，模型继续处理它

兜底：模型没调压缩，或压缩失败 → turn 一结束就投回扣住的输入。不能卡住。

两个数字在仓里已有名字，不要新造：ACCEPT_TASK_BOUNDARY_THRESHOLD = 128_000、CLOCK_REFRESH_INTERVAL_MS = 1_800_000。唤醒与扣件机制也现成（idle ? followup : steer；扣件今天绑在换代上）。
成本提醒：pre-step 在 turn 启动的关键路径上，而 jev 默认超时 30 秒 × 重试 3 次。这条用途要更紧的配置；判不出要"不压"并显式记一条，不装成安静。
