# 可执行审查题目

请对当前 `dsh-agent-team` 设计并执行一次**以证据为依据的 Agent 可维护性与检查有效性审查**。目标不是增加规则或列出更多问题，而是回答：

> 一个不了解仓库的 Agent，能否从真实维护任务找到正确入口，以局部、可理解的改动完成工作；当改错时，现有测试和检查能否以正确理由拒绝它？

以“单个手写代码文件不超过 800 行、单行不超过 200 字符；名称符合领域搜索；测试能识别错误；确定性规则交给脚本”为候选要求，但先验证这些要求在本仓库中的适用范围、例外和实际收益。不要把候选要求当成已经生效的仓库规则。

## 一、权限与完成边界

本轮是审查，不是整改。允许读取源码、测试、配置、历史与官方资料；允许在 `.scratch/active/agent-maintainability-review/` 写审查材料；允许在隔离副本中添加临时探针和实现变异以验证命题。不得修改主工作区业务代码、现有测试期望、AGENTS、CI 或 hooks，不得提交、推送、改 PR、发布或部署。

保留当前未提交 UI 改动以及相邻 Harness checkout 的现有文件。只使用隔离 profile/存储，不能读取或改写真实用户 Session 数据。检查或 browser 工具若会生成文件或临时修改相邻仓库，先按仓库文档确认隔离方式；无法保证隔离就报告障碍，不运行。

完成标准是形成一组可复现、经反证复核的结论和有理由的建议，不要求凑够问题数，也不声称证明全仓无缺陷。

## 二、先建立可复查的基线

1. 阅读仓库 AGENTS 和 `docs/README.md`，只用维护文档导航；当前行为以源码和测试核对，正确性以明确的用户/调用方契约、已有缺陷证据和匹配版本的 Harness 契约判断。
2. 固定实际审查快照：Team/Harness revision、tracked diff、必要 untracked 内容、lockfile、Node/pnpm 版本。若存在工作区改动，HEAD 与工作区分开标识；实验副本必须包含被审查快照，不能用干净 HEAD 冒充当前工作区。
3. 全量盘点源码、测试、脚本的文件/行长度，单列生成物、vendor、声明文件和框架入口。定义文件范围、换行和字符计数；报告全部超限清单，不只列 top-N。生成物不直接整改，必要时检查生成器。
4. 读取检查器源码，画出“声明规则 → 实际检查范围 → package 命令 → CI 触发 → 真实 run → required checks”的执行链。通过 `gh` 只读核对远端事实；缺权限明确标为未验证。
5. 先运行最窄必要的基线检查；记录已有失败和环境障碍。基线不稳定的路径不能直接开展变异评分，更不能靠改期望让它通过。

## 三、深查少量高价值路径

机械盘点覆盖全仓，人工深查明确限制为最多三条端到端路径，不宣称等于全仓深入审计。依据真实风险和近期修改历史选取，当前优先候选是：

- Host 权限、幂等操作、ledger 持久化与重启重放；
- Team preset 与普通 Session 的隔离；
- Client Remote/slot 的进入、退出、卸载及普通 DSH 恢复。

每条路径交付同一条证据链：**用户可观察要求 → 调用入口 → 状态/副作用 → 现有断言 → 能证伪要求的最小实验**。扩大范围前说明哪项新证据使扩大必要；不要按包平均分工，读完大量文件却不验证任何命题。

### A. 可搜索性与修改范围

- 从真实维护任务或历史缺陷的自然语言描述开始，让未知答案的 reader 用 `rg`/符号搜索定位入口、实现和测试。保留原始查询、误命中、漏读点和必须理解的文件；不向 reader 提前泄露答案路径。
- 审查超长文件承载了哪些责任，以及这些责任的真实调用者和变化原因。比较拆分与保留的具体得失，不能为了低于 800 行制造转发层、重复状态或跨文件时序约束。
- `data`、`types`、`config`、`utils` 等名字只能作为调查线索。结合可见范围、目录领域、调用方搜索和项目约定裁决；区分局部变量、公开领域符号、框架入口和稳定导出。
- 若建议改名或拆分，指出一个实际维护任务会少搜索什么、少理解什么或避免什么错误，并计入调用方迁移成本。无法说清收益时，建议保留。

### B. 测试是否真能识错

- 读取断言、fixture、mock 与运行配置，检查结果值、错误语义和 durable side effect 是否被观察；避免只凭 `toBeDefined`、snapshot 或 mock 调用次数就定性，必须结合测试目的判断。
- 先记录期望的独立来源；禁止让测试调用被测函数生成自己的期望，也不能从当前输出倒推正确值。历史中放宽期望的提交，要连同原始需求和修复理由核对，不能一概判错。
- 对每条选中路径挑选有真实业务后果的定向变异，例如忽略权限拒绝、重复写入已提交操作、遗漏卸载释放。每次仅变更实现的一处语义，保留测试不动，并验证变异确实可达。
- 记录 **green → 注入错误 → 目标业务断言 red → 还原 → green**。只因语法/类型错误、启动失败或超时而红，不计为业务识错成功；对存活变异区分真实漏检、等价变异、未执行到与实验无效。
- 优先使用现有 Vitest、存储适配器和可控异步工具。不要先安装全仓 mutation 工具，也不把覆盖率或 mutation 分数当结论。
- 涉及真实产品组合的结论，通过匹配版本、临时 profile 下的现有 browser 路径验证。操作前核对隔离和共享资源；观察实际 DOM/console/持久化及普通 DSH 恢复，截图仅作辅助证据。

### C. 自动检查是否真正约束规则

- 区分可确定的规则与需要判断的要求：行数、行长、已定义的禁止依赖等可机械判断；名称是否贴合业务、拆分是否有益、期望是否正确不能仅靠字符串规则决定。
- 对现有检查和建议新增的检查都设计正负对照，运行真实 CLI。记录合法输入是否误报、非法输入是否漏检、退出码和定位信息；检查 TypeScript 语法变体、作用范围、路径差异和被跳过的文件。
- 如果采用 800/200 限制，给出可复查的存量基线方案：已有超限文件每个 revision 不得增长，改善后收紧，达标后移除例外；重命名不能重置基线，不能自动接受更差的新基线。逐文件/逐行记录不能变成可被挪行绕开的粗总量；说明行长存量债务怎样保持可追溯。不要现在安装这套规则。
- 本地 hook 只作快速反馈，CI 才是服务端执行点；核对 branch protection/rulesets 才能说是合并门。不能通过推送 master、修改保护或开 PR 来验证。
- 优先扩展现有检查或复用现有 TypeScript 解析能力。每项建议说明约束的具体失败、误报/漏报边界、执行成本、责任文件和最小验收样例；没有收益证据就不新增规则。

## 四、subagent 组织

主 agent 负责固定基线、选择路径、理解各方证据并作最终裁决，不能把方案综合和整改判断一起外包。

使用三名职责明确的调查者：

1. **搜索与职责调查者**：做盲查任务、超长文件职责与调用关系分析；不重复跑测试。
2. **测试调查者**：负责选中路径的期望来源、断言审查与隔离实验；不改测试期望。
3. **检查执行链调查者**：负责检查器正负对照、实际命令与 CI/required checks；不重复做领域缺陷审查。

每个调查者写独立材料，不共同编辑结论文件。候选结论有证据后，交给没有参与发现的调查者反驳；必要时按需启动一名复核者，不为每条结论复制多名投票者。复核要寻找合法反例、运行反证或指出契约不足，不以多数同意代替验证。某项证据完整后即可复核，不等待其他方向全部结束。

主 agent 检查实际 patch、输出与断言，并合并根因相同的发现。不得预设缺陷数量；允许“没有成立的问题”“现有取舍合理”。

## 五、交付与证据要求

工作项仍使用 `.scratch/active/agent-maintainability-review/README.md` 作为唯一接续入口。调查材料写入 `materials/`，最终报告为 `report.md`；临时探针、patch、完整日志放 `.scratch/local/agent-maintainability-review/`，报告保留重建方法和关键结果，不搬入业务 tests 或历史 archive。

报告按用户影响和维护成本排序，区分：**已证实缺陷 / 已证实的检查缺口 / 有依据的维护改进 / 待验证假设 / 合理保留**。每项必须有：

- 所属快照与 `path:line`；
- 要验证的要求及独立来源；
- 具体失败或维护成本，以及触发条件；
- 复现命令、输入/变异、预期与实际结果、必要的退出码/断言；
- 反证尝试与裁决；
- 最小安全处理路径、保留现状的取舍、验证方式；
- 尚未覆盖的环境和条件。

另外交付：完整机械清单、所选/未选路径、检查执行链、变异实验结果表，以及建议自动化/保留人工判断的规则分工。计数仅陈述观察范围，不给全仓综合分数。

最终报告前再次核对主工作区 diff 未被污染、临时实验已还原、命令输出来自同一快照。不能运行、没有权限或正确要求未确定的内容明确写“未验证”，不能用另一个 agent 的认可、旧截图或绿色测试总数补齐证据。
