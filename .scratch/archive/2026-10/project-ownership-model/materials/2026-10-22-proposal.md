# Project ownership model：方案草案

> 日期：2026-10-22。本文是本轮研究和方案草案，不是已确认 spec，也不定义当前行为。只有讨论收敛后，才把结论搬到 `spec.md` 和 `docs/`。

## 1. 判断

方向成立，但不能把它当作 Channel 改名。它同时改变四件事：

1. Workspace participation 从“能否进入某个 Channel”收敛为访问授权。
2. Project owner 成为项目级责任，而不是由发言、Claim 或 Attention 猜出来的角色。
3. 主对话与 Thread 分离；新 Thread 变成显式的工作上下文。
4. Inbox、Attention 和 wake 分离：Inbox 记录需要处理的事实，Attention 表示个人订阅，wake 只处理需要即时介入的事实。

旧模型的核心问题不是参与关系本身，而是多个概念共用一个位置：

```text
旧模型：Channel membership / Thread Attention
        同时承担可见性、协作资格、通知订阅和参与历史

新模型：Workspace participation  → 访问范围
        Project owner            → 项目责任
        Thread participant       → Thread 协作资格
        Claim executor           → 当前执行方向
        Task accountable owner   → 交付推进与验收责任
        Thread Attention         → 个人普通通知订阅
        Inbox / wake             → 事实消费与运行时投递
```

这能解释本次改变的动机：实际审计中，Agent 发言量已经高于 Human，Agent 间回复占 Agent 回复的一半以上，但 Task 的 accept/close 仍全部由 Human 完成。系统有很多“参与”，却没有可靠的“谁负责推进、谁不能自验、何时需要介入”的制度。

## 2. 推荐的长期模型

```text
Workspace（访问授权域、共享工作目录）
└─ Project（长期责任范围，原 Channel 的稳定身份）
   ├─ owners：Human 必在；Agent 由 Human 指定；可多个
   ├─ Main stream：项目级报告与协调，不创建 Thread
   └─ Threads：显式打开的协作上下文
      ├─ Discussion
      └─ Task overlay
         ├─ accountable owner：一个推进和验收责任人
         └─ Claims：一个或多个执行方向
```

推荐的职责边界：

| 概念 | 负责的问题 | 不负责的问题 |
| --- | --- | --- |
| Workspace participation | Member 能否访问 Workspace 内的 Project | 谁负责项目、谁收到每条消息 |
| Project owner | 谁能发起 Thread/Task、谁负责项目推进 | 谁亲自执行每个 Claim |
| Thread participant | 谁能在 Thread 中协作、邀请同 Workspace Member | 是否必须接收普通更新 |
| Claim executor | 谁正在做一个具体方向 | 谁验收整个 Task |
| Task accountable owner | 谁必须推动 Task 到完成并组织验收 | 是否亲自写代码 |
| Attention | Member 是否订阅 Thread 的普通更新 | 是否有 Project 责任 |
| Inbox | 哪些 durable facts 尚未处理 | Model 是否已经读到或回复 |
| Wake | 哪些事实需要运行时即时介入 | 事实是否已被处理 |

## 3. Project、主对话和 Thread

### 3.1 Project 身份和兼容策略

建议产品和领域统一使用 **Project**，但第一轮不改 durable ref 的值和前缀：

- 现有 `channel:<uuid>` 是历史引用和消息正文中的稳定身份，继续有效。
- 新代码可以把内部概念逐步改为 Project，但第一轮保留 `channelRef` 作为存储和 Remote 兼容字段。
- 新操作不再产生“Channel membership 是新权限”的语义；旧 `team/channel-member-*` 只为 replay 和历史清理保留。
- 不同时维护两套 Project/Channel 行为，也不把旧 Channel 复制成一个新的 Project。

原因是 ref 是身份，不是显示名称。为了改名而替换 ref 会破坏已有消息、Task、引用和外部用户的本地数据；把所有字段机械改名则会扩大变更面，却不会改善协作模型。

### 3.2 Main stream

建议 Main stream 是 Project 下独立的消息流，不把它伪装成普通 Thread：

- 没有 Task、Claim 或 Thread Attention。
- 有自己的 revision 和每 Member read watermark。
- Project owner 可以连续发言和回复。
- 非 Owner 不获得默认发言权；需要报告时使用显式 `report` 意图，Host 可以把报告路由给 Project owner。
- 普通 Project message 不自动创建 Thread。
- 只有显式 `start Thread` 才创建 Discussion 或 Task Thread。
- Main stream 的 reply 只能引用同一 Main stream 的 Message。

不要用“一个特殊 Thread”替代 Main stream。当前 Thread 需要 anchor、Thread revision、Task overlay 和 Attention；把 Main stream 塞进去会让空主对话、主对话 read watermark、Task/Claim 禁止条件都变成隐式特例。

### 3.3 旧数据的主对话处理

旧版本每条顶层 Message 都已经创建了 Thread。迁移时不合并这些 Thread：

- 旧 Thread 保留原 ref、Message、Task、Claim、Attention 和历史 revision。
- 它们在新 Project 下作为 legacy discussion/task threads 继续可读、可继续处理。
- 新 Main stream 从空状态开始，或在首次写入时惰性建立。
- UI 可以提供“历史 Threads”入口，但不能通过重写 ledger 把旧 Message 重新挂到 Main stream。

这样迁移不会改变旧 Message 的 Thread 归属、未读水位、Task 状态或引用目标。代价是升级后主对话不是旧顶层消息的合并视图；这需要在迁移说明中明确。

## 4. 权限和参与关系

推荐的权限层级：

| 动作 | Human | Project owner Agent | Thread participant | Workspace Member |
| --- | --- | --- | --- | --- |
| 读 Project 全部内容 | 是 | 是 | 是 | 是 |
| 写 Main stream 普通消息 | 是 | 是 | 否 | 否 |
| 发送显式 Project report | 是 | 是 | 是 | 是 |
| 开 Discussion Thread | 是 | 是 | 否 | 否 |
| 开 Task Thread | 是 | 是 | 否 | 否 |
| 邀请同 Workspace Member 进 Thread | 是 | 是 | 是 | 否 |
| Claim / 执行 Task | **待拍板；当前实现拒绝 Human Claim** | 是 | 是 | 是 |
| 转交 accountable owner | 是 | 是（目标 Project owner） | 否 | 否 |
| 验收 / close Task | 是 | 是，但不能验收自己执行过的 Task | 否 | 否 |
| 增删 Agent Project owner | 是 | 否 | 否 | 否 |

需要新增或明确的关系：

- `Thread participant` 是协作资格，不等于 Attention。
- Member 在可见 Project 内通过 `team_attention follow` 自助加入 Thread；`unfollow` 只停止普通更新，不撤销 participant。
- Claim executor 和 accountable owner 自动获得该 Task Thread 的协作资格，但不自动成为 Project owner。
- 正文 `@Handle` 是通知，不应同时偷偷授予 Thread 写权限。未 participant 的 Member 直接 reply 会收到 `thread_participation_required`，然后 follow 再重试；第一版不需要独立 invitation 流程。
- 旧 Thread 的 participant 可由历史 Attention observation、Message author、Claim owner 和旧邀请事实归一化；旧 Channel membership 不自动变成所有 Thread 的 participant。

## 5. Owner、Task 和验收

### 5.1 Project owner

- Project 至少有 Human owner，Human 不能被移除。
- Agent owner 只能由 Human 增删，并且必须参与该 Workspace。
- Agent suspend 时保留 owner 关系；责任不消失，但通知需要 fallback 到 Human。
- Agent leave/archive/remove 时，不能静默移除仍承担 Task 的责任；同一个 durable operation 必须携带 Task 转移表，或者拒绝 owner 移除。
- 多个 owners 不建立隐含顺序。需要默认责任人时，使用显式 `accountableOwner`，不要按数组第一项猜。

### 5.2 Task

Task 继续是 Thread overlay，不拆成独立容器。它增加：

- `accountableOwner`：一个长期责任人。
- `sourceThreadRefs`：创建时写入、顺序稳定、之后不可改；建议只允许同 Workspace 的 Thread。
- 可选的 `brief` / `acceptanceCriteria`，用于交接，不把上下文复制到另一个 Session。
- 不增加 completion report；Task Thread Message、Claim Activity 和 Task status activity 表达执行结果。

Claim 仍保留当前项目刻意偏离 Raft 的多方向并行语义：

- Claim owner 是 executor，不是 Task owner。
- Claim 的历史不能擦除；只要 Agent 曾经持有过该 Task 的 Claim，就永远不能作为 Agent 验收该 Task。
- `release` 不等于“从未执行过”。
- Task status 继续由 Claims 派生，避免重复维护状态权威。

推荐的 accountable 默认值：

- Agent owner 创建 Task：默认自己。
- Human 创建 Task：要求显式指定；UI 可以预填某个 owner，但 Host 收到的请求必须是明确值。
- 没有合适 Agent owner 时：Human 作为 accountable owner 是合法兜底。

这比“Human 创建时默认 Human”更符合“Human 定义目标，Owner 负责推进”，也避免从无序 owners 数组隐式选人。

### 5.3 来源和完成

- Task 可以由一个讨论派生，也可以由多个来源 Thread 汇总；来源只保存 ref 和创建时的短快照，不嵌套 Thread。
- 来源 Project 被归档后，Task 仍存在；是否显示 tombstone 需要单独改变当前“归档后 ref 不可达”的契约，不能只在 Client 加一行文案。
- Task 不要求 completion report；进入 `in_review` 和 accept 仍由现有 Task/Claim 状态与 Thread facts 表达。
- 来源 Thread 的“Task 已完成”通知只作为辅助事实，不能成为验收正确性的唯一来源；来源已关闭或归档时不能强行写入。

## 6. Inbox、Attention 和 wake

建议把通知链路固定为：

```text
durable operation
  → Inbox projection
  → wake eligibility
  → safe-boundary delivery attempt
```

第一版推荐的 wake 表：

| 事实 | 默认 Inbox | 默认 wake |
| --- | --- | --- |
| 普通 Main message | Project owners | 否 |
| 显式 Project report | accountable/Project owner | 是 |
| 普通 Thread message | 当前 Attention followers | 否 |
| direct mention / reply target | 被指向 Member | 是 |
| follow / join | Member 自己加入 Thread | 是 |
| Claim done，Task 进入 `in_review` | accountable owner、Human fallback | 是 |
| Claim release，Task 仍未完成 | accountable owner、Human fallback | 是 |
| Task reopen | accountable owner | 是 |
| accountable owner 变更 | 新 accountable owner | 是 |
| Project owner 变更 | 新 owner、Human审计面 | 否或一次性提示 |

这会主动禁止一个高风险循环：

```text
Owner A 普通发言 → wake Owner B → B 普通回复 → wake A → …
```

普通消息只进入可拉取的 Inbox；只有 direct、follow 加入确认、责任跃迁和验收相关事件才打断。Running Agent 只在安全边界 steer，不中断当前 tool call。

新模型移除 `@all` 的特殊展开；新正文中的 `@all` 按普通文本处理，旧 Message 的 recipient snapshot 不重算。

## 7. Reminder

待验收积压和停滞提醒的方向合理，但“账本状态派生”不能单独产生 wall-clock 事件。建议分两层：

### 先落语义，不先承诺准时

- `in_review` 且 accountable owner 处于可确认的 idle 状态，形成待验收 episode。
- `in_progress` 且 Task Thread 长时间没有公开进展，或 Claim executor 长时间 idle，形成停滞 episode。
- “重启后 idle 未知”不直接判定停滞，避免误报。
- Todo 无人 Claim 先作为 Project backlog，不强制创建时指定执行者。

在 Task/Member 的新 operation、activation、Inbox read 或现有 Host wake 时评估 episode。每个 episode 只产生一次提醒。

### 需要准时提醒时

由 plugin 自己增加一个 Host-local evaluator，不改 Harness：

- 一个全局 timer，不给每个 Task 建独立 scheduler。
- durable `reminder-raised` operation 或等价的 private marker。
- episode key 至少包含 `taskRef`、提醒类型、责任人和 condition baseline。
- restart 后从 ledger 重建；运行时 idle 未知时保守跳过。
- Agent 不可用时转 Human，并在事实中标明“原责任人不可用”。
- reminder delivery 失败不影响业务 commit，也不重复写同一业务事实。

精确的 30 分钟 / 24 小时阈值建议等第一批试用后再冻结。现有文档明确禁止时间驱动自动行为；这不是上游限制，而是本插件当前契约，需要在接受提醒方案后有意改写。

## 8. 兼容策略

目标是“新版本能可靠打开旧数据”，不是保留两套长期行为。

### 旧 ledger

- 旧 `team/channel-*` operation 全部继续 schema 解析、replay 和 validate。
- 载入投影时，旧 Channel 归一化为 Project，owners 默认只有 Human。
- 旧 membership 只保留历史 replay 语义，不成为新 Project 的权限依据。
- 旧 Thread、Task、Claim、Attention、Message 不重写、不合并、不重新解析 mention。
- 旧 Task 的兼容读取视图把 `accountableOwner` 解释为 Human，保留现有 Claim executor；这个默认值不回写旧 operation，也不注入旧 `team/thread-read` snapshot。要交给 Agent 必须由 Human 显式转交。
- 旧 Task 的 `sourceThreadRefs` 默认为空，不能从相邻消息猜来源。
- 旧 recipient snapshot（包括旧 `@all` 的展开结果）和历史 unread 不重新计算；新版本不再产生 `@all` 的特殊展开。

### 运行时和发布

- 新 operation kind 可以是 additive durable format；旧数据仍可读，但升级后不能承诺旧 bundle 继续打开新记录。
- 发布前必须备份 `agent_team.sqlite`，并在升级说明中明确“支持向前迁移，不承诺降级回写”。
- 不改 `../deepseek-harness`、agent loop、shipped preset 或上游 Session/Workspace 数据。
- Remote、preset、tool 和 Client 在同一 plugin bundle 内一起更新；Typert 继续由 declaration 生成。

## 9. 实施顺序

建议把原来的三批拆成四个可回滚观察点：

1. **Projection compatibility**：旧 Channel → Project 的载入归一化、owner 默认 Human、旧操作 replay；不改变用户写行为。
2. **Project authority**：owner 管理、Workspace-wide visibility、显式 Thread start、Main stream；旧 Thread 保留为 legacy surface。
3. **Task accountability**：accountable owner、转交、自验禁止、source refs、Task status broadcast、Project/全局 Task view。
4. **Responsibility delivery**：Inbox cause、wake matrix、reminder episode、Host-local evaluator。

每一批都必须有旧 ledger fixture、重放后再次提交、幂等 collision、owner lifecycle、workspace leave、archive/remove、Session restart 的测试。Main stream 组装完成后才需要 browser acceptance；UI 不是本轮模型决策的前置条件。

在进入实现前，`spec.md` 还必须补齐五个 durable 契约，而不能只写产品表格：

1. Project owner 的快照/增删 operation、旧 Channel 的 Human-owner 归一化、replay validator 和 lifecycle transfer。
2. Main stream 的 message/ref/revision/read receipt/inbox 形状，以及它与现有 Thread `unread_required`、`baseRevision` 的关系。
3. Thread participant 的唯一 authority；不能同时引入 participant 表又继续用 `everParticipatedFrom()` 做权限判断。
4. Task status activity、source status fact、多个 Thread revision 的原子性和归档边界。
5. Inbox projection 与 wake eligibility 的记录方式，确保 Inbox 仍是 ledger 派生投影而不是第二个 durable store。

## 10. 本轮需要 Human 拍板的问题

以下按阻塞程度排序。默认方案就是本文推荐值：

1. **Project ref 是否保留 `channel:<uuid>`？** 这是兼容不变量，不建议为改名替换 ref；推荐保留值和第一轮 `channelRef` wire 字段。
2. **Main stream 是否作为独立 stream？** 推荐独立，不伪装成特殊 Thread；旧顶层 Thread 不合并，Main stream 从新数据开始。
3. **非 Owner 如何发主对话？** 推荐显式 `report` action，不靠 prompt 约定；report 直接形成 Owner responsibility fact。
4. **Thread participant 的唯一 authority 是什么？** 推荐新增 participant durable fact；`team_attention follow` 同时创建 participant 和 Attention，Attention 只决定后续普通通知，第一版不增加 invitation 流程。
5. **Human 建 Task 时是否必须显式指定 accountable owner？** 推荐是；没有 Agent owner 时允许 Human 兜底。
6. **Human 是否能 Claim？** 当前实现拒绝 Human Claim；建议第一轮保留该行为，另把“Human 可执行并可自验”作为单独决策，不混进 ownership 重构。
7. **旧的进行中 Task/Thread 如何继续？** 推荐保留旧 Thread/Claim 的继续执行资格；Project owner gate 只约束新 Thread/Task 的发起，直到明确迁移转交。
8. **completion report**：本轮明确不增加；Task Thread Message、Claim Activity 和 Task status activity 足够表达执行结果。
9. **来源 Thread 完成事实如何跨多个 Thread 原子写入？** 推荐先把 source refs 作为不可变导航事实；是否向每个来源追加完成 Activity，需要单独定义多 Thread revision 和归档边界。
10. **提醒是否正式引入时间驱动 durable 语义？** 推荐第一批只做事件触发评估，试用后再决定是否启用 plugin-owned timer；这比只问“有没有 timer”更基础。
11. **升级后是否需要旧版本二进制降级打开新 ledger？** 推荐不承诺降级，但要求备份、forward migration 和明确提示；具体归 release policy，不作为领域模型分支。

## 12. 2026-10-22 用户修正

本节覆盖本文前面仍建议 `report action`、completion report 或“所有普通消息都 pull-only”的旧草案表述；最新细节见同目录 `2026-10-22-inbox-delivery-model.md`。

1. Main stream 独立于 Thread。
2. Project member 不是 Workspace 全部 Member。被 Project 内结构化 mention 过，或已经获得 Thread participant grant 的 Workspace participant，可以 view Project。
3. 为保持外部用户升级后的访问连续性，旧 Channel 显式 membership 作为一次性 `legacy-channel-member` visibility seed 保留；新版本不恢复旧 membership 写入口。
4. Project member 可以直接向 Project Main stream 发消息，不需要额外的 `report` action。
5. Main stream 消息进入 Project owners 的 wake/steer 路径，但不进入非-owner Project member 的 Inbox，也不 wake/注入非-owner Project member。
6. Task/Discussion Thread 的普通消息对非-owner follower 是 `immediate`：进入 Inbox，并在 idle 时 wake、running 时 steer。对 Project owner 或 accountable owner，普通消息先进入 Inbox，不立即 wake；达到阈值后才注入 bounded summary。
7. Main stream、direct mention、follow 加入确认、Task status event 和责任变化是高优先级通知。Inbox 默认不等于 runtime delivery。
8. 不增加 completion report。Task status、Claim Activity 和 Thread Message 足以表达执行结果。
9. `sourceThreadRefs` 的 Task 状态跃迁可以向 source Threads 写入结构化 status activities，供 owners、followers、Agent context 和 UI 读取；多个 source Thread 必须由一个 Host atomic operation 更新。第一版建议 source refs 限制在同一 Workspace、同一 Project。
10. Reminder 第一阶段只做事件驱动评估，未来再考虑 plugin-owned timer。
