# Agent 工具与上下文呈现：已确认设计

**确认日期：2026-10-29。** Human 已确认目标、具体行为和六段完整流程；本稿将讨论整理为实施依据。同日另行授权推进实施；进度见 README。本稿不描述当前产品行为，现行行为仍以源码、测试和正式文档为准。

## 1. 目标与范围

首要目标是 Agent 正确理解当前状态并完成协作；其次是减少重复上下文、重复读取和无效重试。不以整体压缩比例驱动改造，不因文字缩短就判定成功。

范围覆盖七个 Team 工具、Agent 通知、Member 动态 context、persona 与 core skills。有证据的行为问题可以修正，但行为变化与文案整理分别验证。保留七个工具的职责、权限、Attention 和 Task/Claim 语义；不改 Human Web Client 交互、不改 Harness 仓库、agent loop 或 shipped defaults。

工程细节由实施者决定：优先复用现有能力，选能够长期保留的最简单实现，不为假设需求引入通用框架、配置开关、备用实现或独立事实数据库。

## 2. 三个不同的状态

| 状态 | 含义 | 不意味着什么 |
| --- | --- | --- |
| 当前上下文已提供某事实 | 来源和对象明确，必要内容完整出现在本次模型可用的上下文中 | 不等于模型理解正确，不等于持久已读 |
| 已确认已读 | 显式 `read` 确认的事实，由 Host 写入既有阅读状态 | 不等于事项完成，不改变 Attention |
| 操作已提交 | Host 按当前权限、状态及并发条件提交操作 | 不等于通知送达，不顺带清除未读 |

收到通知、发回复、`history`、`message` 查询和自动背景补充都不主动确认已读。`read` 可以省略当前上下文里已经完整提供的正文，但必须明确确认了哪些内容、哪些正文被省略、还有多少未读。

历史已读不会因压缩而撤销；压缩可能导致 Agent 缺少工作背景，需要重新提供。当前上下文中的完整性只是本次阅读条件的依据，不建立第二套持久未读状态。

## 3. Member 背景与记忆

- 新会话或上下文缺少起步背景时，提供当前身份、Project ownership、Workspace 参与及路径、预算内完整 memory 索引。
- 没有变化时不追加重复内容。
- 自己修改 `memory.md` 后，只提供简短更新提示，明确先前副本不再代表最新文件；不强迫立即读取刚写过的文件。
- 身份、ownership、Workspace 分别更新；ownership 和 Workspace 变化提供各自完整当前列表，包含撤销为空或从多个参与缩为一个的情况。
- 不因责任变化重发 memory，不因 memory 更新重发身份和 Workspace。
- memory 删除、不可读或超过既有预算时，明确异常及读取/维护入口，不继续把旧副本当成当前索引。
- 压缩后按当前实际缺失的类别补足背景；不能因为还残留一条 memory 更新提示，就假定完整索引仍在。
- 记忆是可能过时的参考，不覆盖 Human 输入、Workspace 指令和 Team durable facts。

## 4. 读取与恢复讨论

`read` 负责分批提供未读、显式确认已读，并补足必要的讨论背景；不新增由模型选择的“继续/重新进入”模式。

- 连续讨论：新增事实全文为主，附必要回复对象和当前 Task/Claim 状态，不重复大片历史。
- 首次进入、压缩后背景缺失、无未读但主动查看：提供讨论主题、少量最近原文、必要引用对象和当前状态。
- 背景判断使用当前上下文，不用永久的“以前读过”标记。无法可靠判断时补少量背景，不默认模型记得。
- 背景选取使用原文和既有结构化状态；不额外调用模型生成摘要。
- 背景、当前状态、未读事实明确区分。背景不主动推进阅读状态，也不把 Thread card 当成已读完其 Thread。
- 当前批次的正文及必要回复对象优先于额外背景。未提供的历史和附件给出入口；完整消息不代表附件已读。
- 未读按时间顺序分批，不为了展示最新结论跳过旧的必要事实。

### 4.1 长内容

普通消息尽量完整返回；一批放不下就减少条数。单条本身过长时，明确分段和续读入口，不静默截断。

完整提供之前不确认该消息已读，不凭其预览满足写入条件。`read` 续读在完整提供后确认相应消息；`message` 续读保持查询性质，之后可由 `read` 确认并省略重复正文。一次调用必须前进或明确指向可用的续读动作，不能反复返回同一开头。

返回范围与确认范围必须来自同一次选择。不能先确认整批，再在 renderer 末尾裁掉正文。旧的“最多若干条”不能冒充总文本长度预算。具体预算在实现时按现有约定和样例测定，不新增用户配置。

### 4.2 已提供内容的确认

`read` 是唯一显式确认入口，不新增独立“标记已读”工具。确认当前上下文中完整可见的事实时可以不重复正文；新到的或已不完整可见的内容照常提供。无需每次回复后立刻补调用，可在处理 Inbox 时合并确认。

## 5. 写入条件与错误恢复

对 Thread、Main 和 Task/Claim 使用一致的“所需事实是否完整提供”原则，但不统一它们本来不同的权限或 revision 要求。Main 不因本工作项新增 Thread 写入凭据。

可以满足相应阅读条件的内容：来源和对象明确的完整通知、`read/history/message` 结果、拒绝结果中的完整变化，以及具有必要字段的 Task/Claim 事件。只检查本次操作适用的必要事实，不要求读完全部历史。

不能据以判定完整提供：数量、标题、摘要、截断正文、模型自己的总结或“我看过了”。看板上的当前状态只证明当前状态，不代表相关事件或讨论已提供。

- 拒绝结果完整补齐必要事实后，允许 Agent 重新考虑并提交，不强制重复读取相同内容。
- 结果未补齐时，明确缺失与读取入口，不提供暗示可直接写的凭据或恢复句。
- 凭据不保证成功。提交时仍检查最新未读、权限、Thread revision 和 Task 状态。
- 仅满足写入条件不写持久已读、不消费未读标记。
- 不保留正文子串匹配作为备用判断。必须对应具体事实及实际可见内容，短消息不能因别处出现 `ok` 而误命中。

## 6. 通知

| 类型 | 默认内容 |
| --- | --- |
| 直接提及或回复通知 | 发送者、原文、所属讨论、消息定位、必要回复背景 |
| 普通更新 | Thread/Main 入口及未读数量，不复制正文 |
| Task/Claim 变化 | 操作者、对象、实际变化、变化后状态和与读者的关系；不猜原因 |
| ownership 变化 | 新增或撤销的责任，不顺带重发全部背景 |
| DM | 发送者和原文；不虚构 Thread、不计入 Inbox |

同批合并；直接提及和责任变化优先于普通计数。重要内容被省略时明确说明还有直接信号未展开，并给入口。既有已通知正文不得反复挤占新变化；重启/恢复保留既有可重派生投递语义，不新增投递数据库。

通知预算约束整体输出，包含外层说明和读取入口。正文截断与其完整性判断一致。已提供必要事实时，不统一追加“必须先 read”；是否需要读取按当前缺失决定。通知不确认已读。

通知派发性能由并行工作项负责；本工作项不另写派发器。实施通知票前核实那条线的最新实现，避免覆盖其改动。

## 7. 工具结果与规则放置

### 7.1 操作结果

明确区分：已提交、未提交、已记录但未送达，以及确实无法确认的提交结果。

- 成功给本次变化、必要对象标识和后续凭据，不重放全部正文或规则；没有必要下一步时不硬加建议。
- 部分投递失败不冒充操作未提交，不诱导重发已写入的内容。
- 拒绝说明原因及当前可执行恢复；需要重新判断时不说“原样重试”。
- 只有实际证据不足以判定提交结果时才说“不确定”；不用通用 catch 把所有错误改成不确定，也不为此前未遇到的错误增加完整重试框架。

### 7.2 七工具职责

`team_view` 提供地址目录，`team_inbox` 提供未读入口，`team_attention` 管关注，`team_thread` 提供读取和显式已读确认，`team_message` 管公开发言，`team_dm` 管直接投递，`team_task` 管工作状态。目录、看板和关注结果不扩张成正文读取或第二套写入依据。

### 7.3 规则

规则统一定义，但允许使用位置的必要短提醒：persona 放跨工具规则，工具说明放选择及调用所需契约，参数说明保留必要格式，结果说明本次状态和恢复，core skill 放详细方法和少见情况。不得为了去重让基本调用先依赖读教程。

## 8. 工程落点

Host module 保有事实、权限、阅读提交与写入检查的 interface；tool module 负责参数、Agent 结果和文本。Client 不解析这些文本。共享的内部 module 只承担当前真实重复的完整性判断或渲染，不建通用 Agent-facing 语义框架。

实施依据和 Harness interface 核对见 [工程核对](materials/2026-10-29-implementation-notes.md)。尤其注意：canonical 工具结果不自动持久化；当前 surface 中的最终文本才参与判断；裁剪后 `meta` 可能原样留下，不能只信 `meta`。复用 Session 记录，不建独立的已读事实库。

读取批次与确认需要在 Host 中协调。必要时增加窄的 Agent-owned 读取 interface，复用既有 Host 提交；不让 Session 可见性成为 ledger 重放的输入，不从 Agent renderer 更改 Human 读取行为。既有持久记录保持可重放，不为文案优化改变旧 operation 的解释。

现有公开 seam 不足时先记录具体限制再决定；不访问私有字段、不修改 Harness、不虚构已经存在的承诺。结构选择、字段、预算和内部测试由实施者决定，无需逐项交 Human 拍板。

## 9. 完整流程与验收

[六段完整流程](materials/2026-10-29-accepted-flows.md)是行为验收入口，不是仅比较措辞的 snapshot。

1. 起步、记忆更新、责任变化、压缩后恢复。
2. 普通更新、读取、理解当前分工、领取工作。
3. 直接提及、无需重复正文即可回复、稍后显式确认已读。
4. 旧状态写入被拒、收到完整变化、修改行动后提交。
5. 压缩后进入旧讨论、无未读也能恢复背景。
6. 长消息分段、可继续读取、完整后按动作性质确认。

实现检查使用真实累计的 Session surface；覆盖裁剪、压缩、重启、短正文、跨 Thread 同文、旧凭据、新消息并发、memory 异常及通知上限。只覆盖现实生命周期与公开输入，不为类型已保证的内部值叠防御测试。

模型评测复用既有 harness，使用隔离的合成场景，不上传个人会话语料；接入模型前核实本轮可用且获授权的配置，不复用归档中的凭据。关键指标是目标完成、根据新事实改行动、误调用与恢复次数，其后才是上下文 token/字符、总调用数与耗时。比较同一版本窗口和场景，重复运行并报告样本及波动，不承诺未测的成本比例。
