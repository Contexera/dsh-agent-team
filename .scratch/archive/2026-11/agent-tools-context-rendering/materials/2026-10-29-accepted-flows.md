# 六段已确认流程与验收矩阵

2026-10-29 Human 确认。下列中文是讨论用示例，不要求实现逐字翻译；标识符、数量、角色和事件均为合成数据，不代表实际 Team 状态。行为以 [spec](../spec.md) 为准。

## F1 起步、更新记忆、责任变化、压缩后恢复

```text
开始会话
  身份：@A，负责测试。
  Project ownership：无。
  Workspace：项目目录及读取入口。
  私有记忆：路径、用量、完整索引。

后续步骤无变化
  不再追加同样内容。

A 修改 memory.md
  索引已更新，先前副本不再代表最新文件；需要时按路径读取。

A 被授予项目 P 的 ownership
  ownership 当前列表：项目 P。
  不顺带重发 memory 或 Workspace。

压缩后缺少背景
  补当前身份、ownership、Workspace、最新完整 memory 索引。
  接上本次唤醒原因。
```

**检查**：无变化零重复注入；memory 变化不诱发每步重发；ownership 撤销为空、Workspace 多变一仍明确通知；提示残留而索引丢失时补完整索引；memory 缺失、不可读和超预算明确说明。

## F2 普通更新、读取、领取工作

```text
通知
  项目 P / Thread T 有 3 条普通更新，入口为 team_thread read。

read
  确认 3 条已读，剩余 0。
  主题：发布前兼容性验证。
  当前 Claim：@B 检查 Windows 安装。
  @B：Windows 安装由我负责。
  @human：还需要 Linux 回归。
  @C：Linux 环境已准备好。
  下一次写入凭据：由工具提供。

A 领取 Linux 回归
  Claim 已创建；负责人 A；方向 Linux 回归；active。
  说明本次建立的 Attention，返回新凭据。
```

**检查**：通知无普通正文；第一次 read 足以看到需求和当前分工；不重复 anchor；claim 结果不重放读到的正文；普通 Agent 不因 Team 改动获得这些工具或提示。

## F3 直接提及、直接回复、稍后确认已读

以 Main 为例。Thread 仍要求其既有写入凭据，不从通知猜数字。

```text
直接通知
  项目 P / Main，消息 M，@B：@A Linux 回归完成了吗？

前提
  当前上下文已有所需背景，没有其他缺失的必要事实。

A post 回复
  回归已完成，结果通过。
  工具：已提交，新消息 N，回复 M。
  M 未因通知或回复被确认已读。

稍后 read
  确认 M 已读；正文已在当前上下文中，不重复。
  如有新增 O，正常提供 O。
  说明剩余未读。
```

**检查**：post 不要求重新读取同一正文；没有写入后自动确认；未读可通过 read 清理且不重复正文；期间到达新消息不被顺带跳过。

## F4 旧状态写入被拒、重新判断、提交

```text
A 读完 Thread，准备留言“可以发布”。
B 随后发言：Windows 安装失败，先不要发布。

A 用旧凭据提交
  未提交，展示 B 的完整变化。
  相关变化已完整提供；要求重新考虑，给相应写入凭据。

A 修改行动
  先暂停发布。我来复现 Windows 安装问题。
  提交成功；无需再 read 同一句话。

稍后 read
  明确确认对应事实，已完整可见正文不重复。
```

**检查**：Agent 修改行动而非机械重试；结果与恢复句不冲突；拒绝只展示部分事实时要求继续读取；并发新消息仍重新检查；相同短正文、不同 Thread 不能误判；既有权限和关闭状态仍约束写入。

## F5 压缩后进入旧讨论，无未读也能恢复

```text
用户：继续处理那个安装问题。
A 定位 Thread 后 read。

没有未读，本次不改变未读状态。
主题：Windows 安装失败。
Task 进行中；A 负责复现；B 负责发布包。
近期原文：
  A：路径包含空格时失败。
  B：新版包已生成，等待复测。
更早历史未展示，可通过 history 读取。

A 根据需要直接复测，或查询原复现步骤。
```

**检查**：不因历史已读而只返空结果；不重放全部历史；不额外调用模型摘要；没有新已读 operation；背景查询不改变 Attention；再次 read 且背景仍在时不继续堆副本。

## F6 长消息、分段续读、确认范围一致

```text
通知
  B 提及 A，正文较长；当前只给预览和读取入口。

read 或 message
  消息 M 第 1 段，未完整提供，给续读入口。
  M 尚未因本段被确认已读。

连续续读
  每次前进到下一段；最后一段明确结束。

read 流程
  完整交付后确认相应消息已读。

message 查询流程
  提供全文但不确认；后续 read 可确认并省略已可见正文。
```

**检查**：跨多字节字符不丢正文；预算包含包裹文本和下一步入口；中断、裁剪或压缩导致缺段时不误确认；普通长度一次全文；末段不等于附件已读；有多条未读时不能越过未完整提供的一条推进连续水位。

## 结果表达补充

- DM 已记录但无可投递会话：说明已记录、未送达，不建议盲目重发。
- Host 明确拒绝：说明未提交，不称“可能提交”。
- 实际中断且缺乏提交证据：说明结果尚不确定，给现有核实入口，不新增通用重试系统。
- 已提交但某通知失败：说明已提交及通知状态，不引导重复写入。

## 验收矩阵

| 流程 | 主要票据 | 确定性检查 | 模型行为检查 |
| --- | --- | --- | --- |
| F1 | 01 | 连续 Session 注入、分类撤销、压缩恢复 | 继续工作时使用当前责任和记忆 |
| F2 | 03、06、07 | 通知→read→claim、状态与正文一致 | 理解需求且不重复领取已有方向 |
| F3 | 03、05、06 | Main 通知→post→read、水位不提前动 | 无额外读正文即可回答，稍后正确清理 Inbox |
| F4 | 02、05、07 | 真实写入检查及恢复、并发变化 | 根据新事实修改行动，不只换凭据 |
| F5 | 03、07 | 压缩后无未读 read、背景无额外确认 | 能恢复工作，需要时主动补历史 |
| F6 | 04 | 分段完整性、连续确认、不会卡同一页 | 跟随续读入口，不误称全文已读 |

先在相同合成场景上确定性验证，再运行获授权的真实模型评测；重复样本并报告波动。模型成功不能替代水位和提交检查，绿色单测也不能证明模型真的理解。
