## 方法

1. 在与 Harness 同级的独立 worktree 安装依赖，执行维护中的本地包链接脚本、生成路径配置并构建。
2. 运行完整原始测试，确认 1592 项通过，建立有效基线。
3. 由三个代理分别检查 Host 行为、工具与静态契约、Client 测试；主代理审查候选和断言迁移。
4. 每种故障使用新的独立 worktree，临时修改生产代码，分别运行原始测试和精简后的测试；最多同时运行两个故障实验。
5. 比较实际断言失败，补回删减中遗漏的独特场景，再验证最终工作目录。

实验使用项目自己的 `npm run build` 和 `npm test -- <测试文件>`。Remote 方法改名实验在干净构建后注入，再由 `npm test` 重新生成 Typert，以比较两组生成物测试；其余有效实验构建故障版本。所有故障代码仅存在于临时 worktree。

### 实验中修正的判断

- 通知计划的“追加一条”和“用新的一条替换旧的一条”并不等价。把签名里的序号全部改成零时，第一次删减会漏检；已把同数量替换断言合入保留用例，重新实验恢复失败。
- 两条日志游标测试原来只累计序号，即使跳过重新读取也能得到同一数组。它们现在累计事件类型，能够检查是否读到了替换后的内容。
- 普通通知测试原来只比较硬编码文本。它现在检查实际发送的通知，可以发现正文泄漏。
- 工具清单原来只解析源码声明；漏注册仍会通过。它现在检查真实注册结果，可以发现工具不可用。
- 角标的 tone 属性和实际样式类是两个检查对象。合并时保留了实际 `hairline` 类的断言，并单独注入遗漏样式类的故障确认。
- 第一次正文泄漏实验的替换文本匹配两个分支，工具拒绝执行。该次没有测试结果，已排除；重新指定唯一的 Thread 分支后得到有效结果。
