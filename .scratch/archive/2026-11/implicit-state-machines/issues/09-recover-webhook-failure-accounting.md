# 09 — 重启后补齐 Webhook 失败计数与自动暂停

**What to build:** 当前订阅中一次符合计数条件的 Webhook 耗尽，即使收尾中断也只计一次；同一轮连续失败达到三次，Host 续办一次自动暂停。负责人仍能重放原投递，恢复不自动重跑脚本。

**Blocked by:** [08 存储版本升级](08-version-webhook-settlement-storage.md)，先确定新恢复记录的版本和兼容测试。

**Status:** complete

- [x] 从实际接收入口，分别在失败记录落盘后、计数落盘后、自动暂停的 ledger 写入后中断下一步，再重开同一存储。第一、第二次有效失败后仍可运行，第三次才暂停；失败列表、计数、暂停活动和 Inbox 通知不重复，恢复不重跑原脚本。
- [x] 在覆盖失败列表之前，持久保留这次耗尽是否应计数及其所属轮次。提供方重投仍按失败记录的现有保留范围去重；单次收尾用 Host 接收标识识别。计数与该次已应用的证据同一次写入，自动暂停由现有 ledger 确认。证据只为尚未结束的收尾保留，不累积永久去重表。
- [x] 验证空结果成功和人工恢复清零，以及编辑、人工暂停、删除或归档与收尾交错。编辑在失败记录写入等待期间提交，旧收尾不影响新定义；编辑保留已计入的失败。人工恢复按 ledger 恢复记录划分新一轮。
- [x] 人工恢复提交后注入 checkpoint 清零失败，重启补齐清零，同一请求重试不重跑试运行。第一次有效失败只计为 1。混合定时与 Webhook 的订阅重启时，已到期的定时任务等候未完成的暂停。
- [x] 旧耗尽记录没有计数进度时，保留原计数，只恢复可重放结果。与 08 一同写入未发布的 v5。

额外验收：混合订阅的 Webhook 脚本运行期间，定时任务已经排队；脚本结束后继续占用该订阅的执行槽直到失败收尾。定时任务不会抢在暂停前启动。成功运行自身的清零写入失败、定时脚本跨定义编辑时的调度不在本票恢复范围内。
