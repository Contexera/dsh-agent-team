# 通知容量与回复重开

## 11 · 通知正文有界，事实仍可读取

| 场景 | Agent 实际收到 | 读取与后续 |
| --- | --- | --- |
| 7 条 Main 直接更新中的旧消息挤出正文 | 新更新及未展开的 Main 地址、`team_inbox` 入口 | Inbox 有全部 7 条；读取返回旧正文并清除未读；新直接消息仍唤醒。 |
| 20 条直接更新挤出 Task reminder | 未展开的 Thread 地址及 `team_inbox` 入口 | Inbox 保留 Task reminder；显式读取 Thread 才确认。 |

真实 Harness 测试为 `notification-context` 和 `notification-reminder-context`。省略不等于消费，未发现需要改变自动唤醒和重试预算的证据。保留既有 Task reminder 测试，补足 Main 的可读性与后续唤醒断言。

## 12 · 回复跟随草稿，不跟随页面实例

```text
[讨论 A：已发送，等回执] -- 关闭再打开 --> [原草稿、附件、引用]
        回执还在途，再点发送 -------------> 等同一次结果
        回执丢失，再点发送 ---------------> 用原请求重试
        编辑正文、附件或引用 --------------> 新提交
```

浏览器红灯用例扣住首次成功回执并重开，旧代码在真实 Host 落两条相同回复。修复后，未改动的草稿在同一 Client 生命周期复用正在进行的操作或确定好的原请求。上传、正文、引用、顺序和 revision 都随原提交保留；明确业务拒绝让下一次提交重新读取后发新请求。Host ledger 仍决定结果，Client 不持久化提交状态。确认旧草稿成功时才清理原草稿和恢复的选择；晚到的旧结果不改后来编辑的草稿。

两个真实浏览器回归分别延迟和丢弃 Host 回执，最终都只落一条回复，丢回执时附件保留。Client 侧栏回归另验证重开后不再发的情况下，旧回执会清原附件，但不清后来编辑的正文。

## 13 · 主对话复用同一次提交

```text
[主对话：发送中] -- 看板，再返回 --> [原草稿、发送模式和附件]
       再点发送 -------------------> 等原回执或重试原请求
[订阅页] <-------------------------- 旧 Task 回执不改变当前页
```

真实 Web 旧包在看板往返后重复提交主消息；新包只落一条。Task 的丢回执场景恢复勾选状态与原附件，重试后 Host 只有一个 Task，正常进入看板。主消息、讨论、Task 和 Thread 回复共用提交归属；Project 的模式是单一状态。定向回归另外覆盖晚到 Task 不跳走订阅页、原页成功仍进看板。

## 14 · 旧排序不能在新拖动之后写回

```text
[本地旧顺序 A] -- Host 首读在途 --> [拖动为 B，立即显示 B]
     Host 返回空列表 -------------> 保留 B；不补写旧 A
[写 B 在途] -- 拖动为 C ----------> B 结算后写 C
```

旧代码故障注入红灯两项：空 Host 读取让本地迁移多写旧顺序；同一列表第二次拖动在第一次保存未结算时就发出。新逻辑按列表保存，一次只发一笔，等待期间合并到最新顺序；失败不抹掉较新的本地偏好。验证另外一个列表可以独立保存、首读期间失败的最新顺序仍能重试。未加后台重试，也未改变 Host 设置格式。
