## 目标与范围

同一 Host 下多个 Team 页面能够同时使用，不因通知订阅阻塞普通加载。系统检查导航、草稿、未读和页面生命周期，区分“修复连接阻塞”与“完整多页面支持”；不把后一目标全部塞进第一项修复。

## 进展与结论

- 任务 01 的传输修复已实施并通过独立验收（基线 `796ccba`）：`npm test` 636 通过 / 1 跳过；`npm run build` 通过（含客户端 bundle 纯度门禁）；`npm run test:browser` 两项通过（真实 Web 全流程 32.7s、四同源页面并发 13.0s，成员查询 3–8 ms）；`audit-ui-parity` 与 `lint` 为 0。master CI run 35186303253 双 lane 绿（linux + windows）。
- 回归用例有判别力：把维护中的四页面用例跑在旧实现源码上（保留新测试脚本）为红（第二页 probe 3 秒超时），在新实现上为绿 ⇒ 它确实覆盖原故障，不是空转。
- 验收中发现并修掉一个真缺陷：干净流结束被当成终止性失败，页面会永久不再接收更新（违反 Harness 的 carrier 契约）。修复 `b4915cf` 按 `accepted` 分流为 carrier 错误，并在 `connection/reset` 时重开失败的订阅；真浏览器 2×2 复核——未修版连断网重连都救不回来，修好后自动恢复。真机重启不会留下聋页面（两种关停顺序最终都落到该恢复路径）。
- 已删除旧长轮询、Team 自有退避和按旧版本过滤补读的 `ScopeCoverage`。Host 只保留一个待通知版本；每次开场基线触发补读；最后一位订阅者离开即取消流。
- 桌面与 390×844 截图已检查，留在忽略的 `artifacts/browser/`；界面没有新增控件。
- 原有测试环境的 WeakMap 渲染错误未处理：同一组 Agent 测试在改动前后各出现 48 次，真实浏览器没有对应页面异常。
