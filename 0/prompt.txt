## 2. Key Technical Concepts

### 2.1 架构与三状态

- Team 是 opt-in、外部 Cordis bundle，不修改 Harness。
- `packages/agent-team` 是唯一 Team authority。
- append-only operation ledger 是持久事实来源。
- Session surface 只证明“当前上下文完整提供了事实”，不维护第二套持久已读状态。
- 七工具：
  `team_view`、`team_inbox`、`team_attention`、`team_thread`、`team_message`、`team_dm`、`team_task`
- 只有 `team-member` preset 获得 Team 工具/规则。
- Human 只有 Web Client 控制面，不恢复 slash adapter。

必须区分：
1. 完整事实已在当前上下文。
2. 显式 `team_thread read` 确认已读。
3. Host 已提交操作。

完整通知、history、message、拒绝结果可满足上下文条件，但：
- 不推进水位。
- 不消费 marker。
- 回复／提交成功也不替代 read。
- 新事实、revision、权限、Task closed、验收资格每次写仍重新检查。
- Main 不新增 Thread `baseRevision` token。
- Card／board 当前状态不证明历史事件，也不证明 card 指向的 Thread 已读。

### 2.5 06 正在实现的通知策略

目标范围：
- 不更改投递、covered、合并、恢复、未读语义。
- 不新增队列／delivery database／永久去重。
- 仅通知内容选择、排序、总预算和短身份。

当前实现策略：
- 总通知上限 32768 UTF-16。
- 恢复前缀也计入。
- 预留 2048 给 footer、重要省略提示与读取入口。
- 全局候选排序跨 Thread/Main：
  - priority0：当前缺失的直接 Message、Task/Claim Activity、Main ownership Activity，sequence 新的优先。
  - priority1：当前已完整可见的上述事实，仅身份：
    `already in current context; still unread`
    不重新绑定。
  - priority2：Task reminders。
  - priority3：普通计数和 Main Thread cards。
- 8 个 Thread scope 上限，在全局排序之后应用（主线程已修正 subagent 初版的先 slice）。
- 20 条 detail 上限；短身份、reminder、card 都算 detail；普通计数不算。
- Main scope 不另设数量上限，仍受整体字符限制。
- 普通 Message 不输出正文。
- 文本懒生成，选中前不解析 sender/reply/acceptance 大文本。
- current surface 每次通知只派生一次。
- 被省略 direct 必须保留明确总数及入口。
- footer 路由最多4项，其余写 `and N other scopes`，防止 footer 自身太长被 append 丢掉（主线程已复现修正）。
- footer 当前仍以 append(limit=budget) 写入；2048 预留能装固定提醒+最多4标准 ref 路由。
- 明细最多8 Thread scope可少于8，因为字符先满。
- 截断 Message 有8Ki marker，不绑定；已完整仍在surface则身份省略，不重复长正文。
