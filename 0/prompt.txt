## The controller

New file: `/home/yu/projects/dsh-agent-team/packages/client-agent-team/src/client/thread-controller.ts`

```ts
useTeamThreadController(options: TeamThreadControllerOptions): TeamThreadController
```

Inputs: `workspaceId`, `threadRef`, optional `taskRef`, plus the Remote functions both faces already received (`readThread`, `loadThreadHistory`, `threadObservations`, `subscribeChanges`, `resolveMessageRefs`, `reply`, `putAttachment`), `drafts`, and four surface callbacks:

- `projectMembers()` — roster at send time, for optimistic mention chips
- `memberName(id)` — quote-banner author name
- `onRead?()` — panel clears the feed's unread badge; page passes nothing
- `afterWrite?()` — page re-reads roster/Project view; panel passes nothing

Two optional behavior inputs, each used by exactly one face:

- `openingTarget(facts)` — the page's "first unread Message naming the Human"; absent means open at the newest fact (the panel's behavior)
- the Task-write surface, described below

It returns projection state (`projection`, `task`, `thread`, `currentFacts`, `readFacts`, `olderFacts`, `taskCards`, `followerIds`, `historyHasMore`), read/write state (`loading`, `error`, `pending`, `autoReadExhausted`, `newFactsCount`, `replyTarget`, `replyTo`, `pendingFiles`, `draftKey`, `flashedMessage`), and actions (`readCurrent`, `loadOlder`, `refreshAfterFence`, `refreshPassiveFacts`, `retryAutoRead`, `onTimelineScroll`, `jumpToNewest`, `flashMessage`, `setReplyTarget`, `setPendingFiles`, `clearSendState`, `sendReply`, `commit`, `applyTaskCommit`, `reportError`).

`commit(spec)` runs one durable write under the shared busy gate: it keeps the requestId per key so a lost answer replays instead of writing twice, and it converges on either fence (`unread_required` drains and re-reads; `stale_revision` re-projects passively). `applyTaskCommit(committed)` merges a committed Task write's projection and activity row, then re-reads. It takes the union of the fields promote, accept/close/reopen, and transfer all return, with `claims` optional because transfer's result does not carry them.

## How the differences were reconciled

| Difference | Resolution |
|---|---|
| Page opens on first unread `@Human` Message and pulses it; panel always opens at newest | `openingTarget` option; the jump/flash machinery lives in the controller but only runs when a target is returned |
| Page acknowledges reads to its feed through none; panel calls `onRead(threadRef)` on each successful read | `onRead?` hook |
| Page also reloads roster + Project view after writes; panel does not | `afterWrite?` hook |
| Page has full Task controls (promote, accept with early-accept confirm, close, reopen, transfer); panel only promotes | Controller exposes `commit`/`applyTaskCommit`; each face defines its own writes. Transfer's `landedOn` receipt and refusal copy stay page-only (`useTaskTransfer` unchanged) |
| Page subscribes to `workspace` and `presence` scopes in addition to `thread` | Controller owns the `thread` subscription; those two stay in the page and feed the controller's error surface via `reportError` |
| Page keeps `projectView` and derives `members`; panel receives both as props | Stayed surface-owned; page's supplemental loader and its coalescing round are unchanged |
| Page's follower set seeds the follow control; panel passes `undefined` so the hook asks the Host | Preserved exactly; both still call `useThreadFollow` with `followerIds`/`undefined` as before |
| Panel has an `onPromoted` hand-off on commit; page merges and re-reads | `commit` takes an `onCommitted` callback, so each face decides |
| Promote button label gated by `mutating`, not `pending` (a reply send must not retitle it) | Both faces keep their own local `mutating` state around the `commit` call |

Facts, history cursor, sequence guards, drain cap, unread counting, error cleanup, and reply lifecycle logic were moved verbatim.
